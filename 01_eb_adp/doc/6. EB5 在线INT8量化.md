# 6. EB5 在线 INT8 量化（昆仑 P800，2026-10-21）

> 结论：**43 层整网在 4 张卡上跑通，输出通顺**（`France → Paris`）。
> BF16 整网在 8 卡上是结构性显存墙（见 §2），INT8 是唯一可行解。
> 运行流程见 `3. eb5模型运行.md` §11，性能债见 `4. 临时D2H与性能债.md`。

## 一、结论速览

| 项 | BF16 | INT8 |
|---|---|---|
| 8L 权重/卡（4 卡） | 28.5–30.0 GB | **15.8 GB（−47%）** |
| 整网权重/卡 | 79.5 GB（8 卡）/ 143 GB（4 卡装不下） | **75.0 GB（4 卡，EP4）** |
| 整网 4 卡 | ❌ | ✅ **4/4 HTTP 200，输出通顺** |
| 8 卡预估 | OOM（差 10–128 MB） | **≈41 GiB/卡**，KV 余量 ≈50 GB |
| 精度 | — | 端到端 **1.19–1.68%**（真实权重） |
| 速度 | 1× | **≈2.5× 慢**（per-token quant + int8 GEMM） |

## 二、为什么必须 INT8（BF16 整网的显存账本）

实测（8 卡、43 层）：

```
权重 74.03 GiB + forward 工作区 16.1 GiB + 非 torch(XCCL/DeepEP) 5.9 GiB + KV 0.4–1.5 GiB ≈ 96 GiB
```

- 首个 forward 时 torch 从 16.7 GiB 空闲涨到只剩 56–106 MiB，随后 64–128 MiB 申请就 OOM
- **KV 池走 `kunlun_ops` 原始分配器，不计入 torch 账本** → `ctx` / `mem-fraction` / `max-total-tokens`
  对 OOM 无效（ctx 32768→8192 后 allocated 仍为 90.12 GiB）
- `chunked-prefill-size` 必须被 `page_size`(1024) 整除 → 预填块压不到 1024 以下
- `max_running_requests` 是**全局值**，必须 ≥ dp_size（8 卡时最小 8）

## 三、可用的 INT8 粒度（重要负结果）

昆仑 `kunlun_ops 0.1.227` **没有可用的 128×128 block-scale INT8 GEMM**：

| 尝试 | 误差 |
|---|---|
| `matmul` + block scale `[n/128,k/128]` | 91% |
| 其它 block 布局 | 24%–1625% |
| `m_grouped_gemm_I8_I8_*` + block scale | **NaN** |
| 同一调用 + per-channel `[E,n,1]` | **0.33%** ✓ |
| `gemm_I8_I8_bf16_nt`（文档 `[g,n,k]` 形态） | `ValueError: unsupported tensor shape` |

→ **只能 per-token 激活 + per-output-channel 权重**；显存收益与 block 方案相同（都是 1 字节/元素）。

粒度对比（同批数据）：per-tensor 2.75% → **per-channel 1.74%** → block-W 1.50% → block-W+A 0.97%。

  - `写一句话描述春天。` → `春天是万物复苏、生机勃勃的季节。`
  - 量子纠缠 → `量子纠缠是指两个粒子的量子状态彼此关联…无论它们相隔多远。`

**8 卡整网预估**：权重 79.91 GiB → **≈41 GiB/rank**（−48%）。

## 六、已知限制

1. 无 block-scale INT8 GEMM（精度比 block 方案差 0.3–0.8pt）
2. `EB5_INT8_LINEAR_CPU_STAGING=1` 会让 `kv_b_proj` 占位落 CPU，而 EB5 的 `post_load_weights`
   在量化前用它构造 MLA absorb 缓冲 → 首前向 `mat2 is on cpu`；当前把 `kv_b_proj` 排除在暂存外规避
3. `/update_weights_from_tensor` 不支持 INT8 层（per-row scale 不重分片）
4. `Int8MoEMethod.apply` 只实现 standard dispatch，DeepEP 走插件既有 `forward_int8` 分支
5. 性能慢 ~2.5×（未做优化）
6. 精度只验到 GEMM 级 + 输出通顺，未做 KL/MMLU
7. 昆仑实测：`gemm_I8_I8_bf16_nt` 的官方文档形态（`[g,n,k]`）**不可用**，
   实际走的是 `m_grouped_gemm_*` + per-channel scale
