> ## 🔴 最重要的一条：不要 `kill -9` 卡在 XPU 调用里的进程
>
> **这是本次踩得最惨的坑，请先读这一段。**
>
> 对"卡在 XPU 调用里"的进程（特征：CPU 100% 空转、GPU `0% util`、显存不涨）
> 执行 `kill -9`，会在设备上留下**杀不掉的 kernel** —— `xpu-smi` 显示
> `util = 100%`，但 `xpu-smi -q` 的 `Processes` 是 `None`。这种残留会**拖坏整个
> XPU runtime**：之后连 `torch.ones(1024, device='cuda')` + `sync` 都会间歇性挂死。
>
> 更糟的是驱动会**泄漏 "in use" 引用计数**：此后 `xpu-smi -r`（逐卡 HW reset，
> 官方唯一的用户态恢复手段）对**全部 8 张卡**都报
> `XPU ... is currently in use by another process`，**即使没有任何进程持有
> `/dev/xpu0..7` / `/dev/xpuctrl`**（逐 `/proc/*/fd` 扫过）。于是**只能节点级重启**。
>
> **正确做法**
>
> 1. 发现卡死**先等**（XPU 调用自带超时，给它时间自己出来），不要条件反射地杀；
> 2. 确实必须杀时，杀完要确认 **8 张卡都回到 `0 MiB / 0%`** 再起下一个任务
>    （`xpu-smi | grep 98304MiB`）；
> 3. 服务挂了**不要立刻重试**，先看 `xpu-smi` 是否全绿；
> 4. 脚本里那几行 `pkill -9` 清理逻辑**是有代价的**，只在确认没有 XPU 调用在飞时用。

### 7.2 两个真实阻塞点（都是干净异常，不是卡死）

**① `NotImplementedError: act_quant_kunlun unavailable on the fork`**

`EB5_KUNLUN_ADAPT_DIR`（本文要求 DSV4 也必须设，为了 `_init_raw` 那个 pad 绕行）会加载
`eb5_kunlun_adapt.py`，它注册了一个**假模块**
`sglang_kunlun.hooks.layers.attention.nsa.triton_kernel`，里面只有一个抛异常的
`act_quant_kunlun` 桩（原注释写"只有 `*_kunlun` 变体会用到"）。但 DSV4 的 indexer
量化路径**真的会调它**：

```
deepseek_v4 indexer.compute_q
 → kernel_ops.py fused_q_indexer_rope_hadamard_quant
 → dsv4_torch_shim.py:642 act_quant_kunlun(q_hada_2d, block_size=head_dim)
 → eb5_kunlun_adapt.py:281 → raise NotImplementedError
```

**修法**：把桩换成**能用的自包含实现**（与插件 `nsa/triton_kernel.act_quant_kunlun`
同实现，都是 `kunlun_ops.quant2d`）。改动落在
`01_eb_adp/test/eb5_kunlun_adapt.py` 与 `eb5_extra_adapt.py` 两处。

> ⚠️ **别图省事写成 `importlib.import_module("...nsa.triton_kernel")` 去复用真实现**。
> 那条 import 会拉起 `sglang_kunlun/hooks/layers/attention/__init__.py` 的 nsa redirect，
> **提前 import fork 的 attention 模块**，使适配层 `_TARGETS` 的补丁被**已经绑定的旧符号**
> 绕过。实测后果：`test_eb5_layer_modules.py` 从 **19 passed 退化成 4 failed**
> （`python/sglang/kernels/ops/attention/dsv4/dequant_k_cache.py:68
> TypeError: 'function' object is not subscriptable`）。

**② `RuntimeError: compressed_attention: win_kv_cache dtype must match q`**

`forward()` 无条件把 decode/extend 送进原生算子，但 DSV4 的 SWA KV cache 是
**uint8 字节缓冲**。fork 内存池注释把布局写得很清楚：

```
# BF16 layout: nope (448*2=896) + rope (64*2=128) = 1024 bytes/token
# FP8  layout: nope (448 fp8) + rope (64*2=128 bf16) + scales (7+1) = 584
```

实测 `kv_cache_total_dim = 584`（**FP8 布局**）。插件那段 uint8→bf16 重解释的条件是
`== 512 * 2`（1024，即 bf16 布局），FP8 布局**不命中** → uint8 cache 直接喂给算子 → 报错。

而插件自己的注释就写着 "The fp8 layout has no uniform view and is handled by the torch
paths instead" —— 只是 `forward()` 漏了这个分支。

**修法**：按插件自己的约定，FP8 布局（`swa_k_cache.dtype == torch.uint8`）改走
纯 torch 参考路径（`_dequant_sparse_keys` + `_sparse_mla_attention`）。
改动落在 `sglang_kunlun/hooks/layers/attention/deepseek_v4_backend.py`。

> 这个 dtype 问题**不是图捕获特有的**，关图模式下同样会撞到。之前关图没撞到，
> 只是因为更早的 `act_quant_kunlun` 先炸了 —— 修完①之后才暴露出来。

### 7.4 开图（`llgraph`）为什么还没通

FP8 布局现在走的是 torch 参考路径，而这条路径里有 **host 同步**
（`int(kvseqlen_cpu.max().item())`、index 操作），CUDA graph 捕获大概率不可用。

要真正开图，需要让原生 `compressed_attention` 能直接吃 FP8 布局 —— 那是**算子侧（KLX）**
的事；或者改 cache 的呈现方式（把 uint8 缓冲 `view` 成 q 的 dtype），但后者在混合布局下
**有静默算错的风险**，没有数值对齐手段时不要动。

### 7.5 停机：不要再手写 `pkill -9`

原来的两个 run 脚本里都有：

```bash
pkill -9 -f "sglang.launch_server" ; pkill -9 -f "sglang::"
```

**这段已经删掉**，换成 `01_eb_adp/tool/stop_kunlun.sh`。它有两个真实的坑：

1. **会打到调用者自己** —— `pkill -f` 匹配整条命令行，而调用它的命令本身往往就含这些
   字符串，于是把自己的 shell（甚至父 shell）一起杀掉，脚本半途而废。本次实测踩到两次
   （exit 137 / 143）。
2. **对 launcher 用 -9 会留 stuck kernel**（本文档开头那条）。

`stop_kunlun.sh` 的分级策略：

1. 先给 launcher 发 **TERM+INT**（sglang 有优雅退出 handler）；
2. launcher 主线程通常卡在 `waitpid` 等子进程，而 `sglang::tokenizer_worker` /
   `detokenizer` **不响应 TERM/INT**，handler 永远走不完 —— 这就是"发了信号也退不掉"的真因；
3. 于是**只对这两类空闲的纯 CPU worker 用 -9**，解开 `waitpid` 死锁。
   判据：角色上它们只做分词/反分词、不发任何 XPU 调用；实测状态为 `S` +
   `ep_poll`/`futex_wait`，且 `xpu-smi -q` 不登记它们。状态不像空闲 worker 就**跳过不杀**；
4. **launcher 本身一次 -9 都不发** —— 子进程被回收后它会在几秒内自己走完 handler
   （实测 **5 秒**）；
5. 最后校验 8 张卡都回到 `0 MiB / 0%`，不满足就报错退出，交给人看。

两个 run 脚本现在都通过它做启动前清理，清不干净就直接放弃启动（不硬上）。

### 8.2 第 1 次起服务：首次前向的设备级 kernel 异常

模型 6144 个分片加载完（约 2.5 分钟），**首次前向**即崩：

```
ernie5.py:3644  forward → self._mhc_pre(...)
ernie5.py:3587  _mhc_pre → _mhc_pre(...)
sglang/kernels/ops/layernorm/mhc.py:1176  mhc_pre → kernel_0(...)
sglang-kunlun/01_eb_adp/test/eb5_kunlun_adapt.py:124  kernel_0
    sqrsum_partial[s, :n].copy_((xs * xs).sum(-1))
torch.AcceleratorError: CUDA error: wait for noc idle timeout
kl3ChannelCheckErrors ... status= 299
```

8 个 rank 全崩，scheduler 全部 `exit code -3`。dmesg 里紧跟 **4 个设备**的
`KL_XID_KERNEL_EXCEPTION`（`ch=3`，22:34:18–22:34:31）。

> **注意 traceback 的自我声明**：`CUDA kernel errors might be asynchronously reported
> at some other API call, so the stacktrace below might be incorrect` —— 所以
> `eb5_kunlun_adapt.py:124` 未必是真凶，得用 `CUDA_LAUNCH_BLOCKING=1` 才准。
> 但它把范围缩到了 `mhc_pre` 的 splitk 拆解（`kernel_0`）这一块，
> 与第六节待办里写的"EB5 的 `mhc_pre` splitk 拆解"一致。

形状契约本身是对的（对着 `mhc.py:1120-1180` 核过）：

```
hc_hidden_size=16384, split_k=n_splits_pre=16 → split_size=1024
partial_out   = (16, num_tokens, 32)   → out_partial[s, :n, :j]      (j = min(hc_mult3, ...))
partial_sqrsum= (16, num_tokens)       → sqrsum_partial[s, :n]
xs = xf[:, lo:hi]  → (n, 1024)
```

即切片/矩阵乘的维度都能对上，**不是简单的 shape 越界**，更像设备级 kernel 异常。

### 8.3 第 2 次起服务：退化成 XCCL/D2H 挂死

带 `CUDA_LAUNCH_BLOCKING=1` 重跑（为了定位真凶），结果**在加载权重刚开始就挂死**，
连 XCCL 初始化日志都没有（`XCCL version` 计数 = 0）：

```
[22:38:20 DP4 TP4 EP4] Load weight begin. avail mem=95.75 GB
[22:38:20 DP4 TP4 EP4] EB5 MLA+HCA plan: 44 entries, ...   ← 日志到此为止
```

现场：

| 项 | 值 |
|---|---|
| `sglang::scheduler_DP0/DP1/DP2` | 状态 `R`，CPU **~94% 空转**，持续 12 分钟 |
| 对应 3 张卡 | **util 100%**（另 5 张 0%） |
| 日志 | 20 s 内 **0 字节**增长 |
| `xpu-smi -q` | 登记 **8 个**进程 |

这与第四节的「最小复现」**同型**：`init_process_group(nccl, ws=8)` 场景下
**rank 0/1/2 挂死**。也就是说 8.2 那次 kernel 异常之后，设备就退化了 ——
**"kernel 异常 → 设备退化 → rank 0/1/2 挂死"这条链完整重演**。

### 8.4 本次的处置（安全第一）

- 挂死后**只等不杀**：连续观察 12 分钟（`R` + 94% CPU + 100% util + 日志零增长），确认是永久挂死而非慢
- **全程没有对 launcher / scheduler 用 `-9`**（它们正卡在 XPU 调用里，正是本文开头禁止的动作）
- 第 1 次崩溃后的残留是用 `tool/stop_kunlun.sh` 清的（它只对**空闲的纯 CPU worker** 用 -9，launcher 一次都没挨 -9）
- **未尝试 `xpu-smi -r`**（第五节说它被泄漏的 "in use" 引用计数挡住；且它是逐卡 HW reset，需要人工确认后再动）

### 8.5 结论与下一步

1. **EB5 起不来的根因是 8.2 那个设备级 kernel 异常**，触发点在 `mhc_pre` 的 splitk 拆解
   （`eb5_kunlun_adapt.py:99-127` 的 `kernel_0`）。这是**先于**一切配置问题的硬阻塞 ——
   它就是第六节待办的第一条，本次独立复现确认。
2. 修它的顺序建议：先用 `CUDA_LAUNCH_BLOCKING=1` **在一张卡上**把真凶缩到一个具体的
   `aten` op（本次因为设备已退化，没走到这一步就被 XCCL 挂死挡在前面了），
   再决定是改 `kernel_0` 的写法还是交给 KLX。
3. **设备恢复**：本次是"kernel 异常 + rank 0/1/2 挂死"的组合，按第五节需要**节点级恢复**。
   恢复后再按 7.1 跑一次 XCCL 探针确认 8/8，再谈 EB5。

## 九、更正与补充：设备存在"半坏"状态（2026-10-17 深夜）

第八节有两处结论被后续实测推翻，这里更正。

### 9.1 更正一：挂死**不是永久的**，约 20 分钟后会自行超时退出

第八节 8.3 记的那次挂死（22:38:20 起），到 **22:58:24** 自行收尾：

```
RuntimeError: Rank 0 scheduler died during initialization (exit code: -3)
```

即挂了约 **20 分钟**后，XPU 调用自带的超时兜底生效，进程正常退出、显存释放。
所以 8.3 说的"永久挂死"应更正为"**会长时间挂死（十几到二十分钟），但最终能自己退**"。

> **推论：挂死时更不能 kill。** 你等它 20 分钟，它会干净地退；你 `kill -9`，
> 就变成本文开头那种"引用计数泄漏、只能节点级重启"的局面。

### 9.2 更正二：设备会进入"**通信能通、算力不能用**"的半坏状态

第八节之后，设备已经显示 8 卡 `0MiB / 0%`、8 进程 XCCL 探针 **8/8 通过**。
然后**在单卡上**跑 EB5 单测，`test_mhc_pre_big_fuse_with_norm_tilelang_kernel` 直接挂死：

```
assertTrue (unittest/case.py:685)
test_mhc_pre_big_fuse_with_norm_tilelang_kernel (test_eb5_hc_pre.py:154)
    self.assertTrue(torch.isfinite(post_mix).all())
```

（栈是用 `py-spy dump --pid <pid>` 读的 —— 只读、不发信号，挂死时的首选诊断手段。）

现象：单卡 util **100%**、进程 CPU **101%** 空转十几分钟，**且不产生新的 Xid**。

**这条推翻了一个很自然的假设**：`xpu-smi` 全绿 + XCCL 探针 8/8 **≠** 设备健康。
判据必须再加一个**真实算力探针**（已实现为 `tool/compute_probe.py`：小 GEMM +
逐行平方和 + `isfinite().all()` 同步 —— 正是这次挂死那条路径的同型算子）。

> 同时也说明第五节"需要节点级恢复"的结论**依然成立**：半坏状态靠等、靠探针都回不来，
> 得重载驱动。

### 9.3 恢复判据（更新版）

起服务前必须**四项全过**（`tool/preflight.sh` 已实现，任一不过就拒绝启动）：

| # | 检查 | 判据 |
|---|---|---|
| 1 | 设备空闲 | 8 张卡都 `0MiB / 0%` |
| 2 | 设备未受新伤 | dmesg 的 `KL_XID_KERNEL_EXCEPTION` 计数不比基线高 |
| 3 | 通信可用 | 8 进程 XCCL 探针 **8/8** |
| 4 | **算力可用** | 8 张卡各跑一次真实算力探针 **8/8** |

第 3、4 项**不可互相替代** —— 9.2 就是"3 过、4 挂"的实例。

### 9.4 顺带：`timeout` 也不是护栏

单测那次挂了 19 分钟，而外面包的 `timeout 600` 早在第 10 分钟就发了 SIGTERM ——
**完全无效**（进程卡在 C 调用里，信号处理器跑不到）。所以：

- 别把 `timeout` 当护栏，它只会让你误以为"已经杀掉了"；
- **更不要用 `timeout -k`** —— 那会在超时后升级成 SIGKILL，正好踩中本文开头那条。
