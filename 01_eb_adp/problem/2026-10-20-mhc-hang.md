## 0. 结论

两次挂死都发生在**真实多 rank 首次前向**，都不是 Python 异常，而是**设备侧永久等待**：

| # | 时间 | 卡 | 挂死位置（Python 帧） | 实际卡住的 op | 结果 |
|---|---|---|---|---|---|
| 1 | 11:56:08 | 4/5/6/7 | `eb5_extra_adapt.py:808` `src.index_select(0, src_idx[mask])` | **布尔索引的隐式 D2H**（`aten::nonzero` + 设备→主机同步） | 4 rank 全挂，watchdog 12:03:11 触发，`exit -3` |
| 2 | 12:28:~30 | 0/1/2/3 | `eb5_kunlun_adapt.py:146` `fk = f[:j, lo:hi].t().contiguous()` | **非连续切片转置后的 strided copy**（或紧随其后的 `xs @ fk`） | DP0 卡住、DP1–3 停在 `torch_xmlir` linear；watchdog 12:35:07，`exit -3` |

两次都**没有 `kill -9`**，均由 scheduler watchdog（300 s）自行收尾。但每次退出都会
产生 4 条 `KL_XID_KERNEL_EXCEPTION`，之后整机进入"**任何 D2H 都挂**"的半坏状态：

- XCCL 探针停在 `xccl_probe.py:33` 的 `p8l.cpu()`；
- 单卡算力探针停在 `compute_probe.py:26` 的 `torch.isfinite(c).all().item()`；
- 8 张卡各跑一次算力探针 → **0/8**。

即：**不使用 `kill -9` 也挡不住设备退化**。这是对 `doc/3` 开头那条经验的重要补充 ——
那条说"kill -9 会留 stuck kernel"，但本次是"挂死 + watchdog 退出"同样留下 Xid 与坏状态。

## 1. 挂死 #1：`memcpy_triton` 的布尔索引（D2H）

### 1.1 触发上下文

- 服务：`EB5_GPUS=4,5,6,7`、`tp=dp=ep=4`、`--moe-a2a-backend none`
- 阶段：权重加载完成后的 **warmup 首次前向**（每 DP rank 3 token）
- 时间：11:56:07 XCCL 初始化完成，**11:56:08 日志停止增长**

### 1.3 当时的实现

```python
# eb5_extra_adapt.py（2026-10-20 13:00 之前的版本，:798-809）
r = torch.arange(max_rows, device=dev, dtype=torch.long)
if offset_src:
    src_idx = off + r
    mask = (r < n) & (src_idx < src_rows)
    dst_idx = r
else:
    dst_idx = off + r
    mask = (r < n) & (dst_idx < dst_rows)
    src_idx = r

src_sel = src.index_select(0, src_idx[mask])   # ← 挂在这里
dst[dst_idx[mask]] = src_sel
```

### 1.4 到底是哪个 kernel

挂死的**不是** `index_select` 的计算核，而是 `src_idx[mask]` 这一步：

- 布尔 mask 索引的输出长度**依赖数据**，torch 必须先知道 `mask.sum()`；
- 于是触发 `aten::nonzero` / `aten::count_nonzero`，把结果**同步回主机**；
- 主机侧等 XPU 完成 → 在这个等待上永久停住。

与旧版 `int(offset)` 属于**同一类问题**（device 标量 D2H），只是换成了"数据依赖形状"
的隐式同步。参考：`doc/3` 第四节的最小复现（`init_process_group(nccl, ws≥4)` 后
`p8l.cpu()` 永久挂住），本次是它在真实模型里的表现。

### 1.5 为什么单测没抓到

- 单测是**单进程单卡**，D2H 在那种环境下正常工作（1 秒返回）；
- 旧用例只传 `offset=0, sz=整块, offset_src=True`，mask 全真 —— 语义分支也没覆盖；
- `test_eb5_adapt_coverage.py` 只检查"符号名在测试源码里出现过"，不检查分支。

## 2. 挂死 #2：`kernel_0` 的 strided copy / matmul

### 2.1 触发上下文

- 服务：`EB5_GPUS=0,1,2,3`（因为 4–7 已被 #1 拖坏）
- 权重加载 15 s、`9 entries, full_mla=1(7), hca=7` 的 plan 正确、HTTP 已启动

### 2.3 当时的实现

```python
# eb5_kunlun_adapt.py::mhc_pre_gemm_sqrsum_splitk_kernel 内的 kernel_0（事发版本）
out_partial[:, :n, :].zero_()
for s in range(split_k):                      # split_k = 32（服务默认 n_splits_pre）
    lo = s * split_size                       # split_size = 16384 / 32 = 512
    hi = lo + split_size
    xs = xf[:, lo:hi].contiguous()            # :145  非连续列切片 → 连续拷贝
    fk = f[:j, lo:hi].t().contiguous()        # :146  ← 挂在这里（转置后的 strided copy）
    out_partial[s, :n, :j].copy_(xs @ fk)     # :147  matmul + copy
    sqrsum_partial[s, :n].copy_((xs * xs).sum(-1))
```

真实形状：`n=3`（warmup 每 rank 3 token）、`hc_hidden_size=16384`、
`hc_mult3=24`、`split_k=32`。

### 2.4 到底是哪个 kernel

py-spy 只能给到 Python 行，卡住的 C 调用有两个候选，都在同一段：

1. **`f[:j, lo:hi].t().contiguous()`** —— 先对非连续切片转置，再做一次
   **strided copy**（`aten::clone` / `copy_`，源 stride `(1, 16384)`、目标 stride `(24, 1)`）。
   这是最可能的点：它对每个 split（32 次）都执行一次非规则访存的拷贝。
2. **`xs @ fk`** —— 紧随其后的 `aten::mm`（`(3,512) @ (512,24)`）。

要精确区分需要 `CUDA_LAUNCH_BLOCKING=1` 在**单卡**上复跑，但设备在 #1 之后已退化，
本次没走到这一步。历史上同类现场（`doc/3` §8.2）是在
`sqrsum_partial[s, :n].copy_((xs * xs).sum(-1))` 处报
`CUDA error: wait for noc idle timeout` / `KL_XID_KERNEL_EXCEPTION`，
说明这一族 **strided / 小规模 matmul + copy** 的写法在 XPU 上本身就不稳。

### 2.5 为什么单测没抓到

- `TestHcPreSqrsumFamily` 确实覆盖了 `kernel_0`（16/32 split、token 8/256/2048/2049），
  且在**单卡**上全绿；
- 但挂死是**多 rank + DP attention + 真实 warmup** 才出现的设备级等待，
  Python 层没有任何异常，单卡无法复现；
- 单测用的 token 数最小是 8，**服务 warmup 是 3**（`doc/3` §12.3 已记过这个盲区）。

## 3. 为什么整机被拖坏（时间线与证据）

| 时刻 | 事件 |
|---|---|
| 11:51 | 4–7 preflight：设备空闲 + XCCL 4/4 + 算力 4/4 **全过** |
| 11:56:08 | **挂死 #1**（4–7，`memcpy_triton`） |
| 12:03:11 | 4 个 scheduler watchdog 超时 |
| 12:03:18 | `scheduler_0 crashed with exit code -3` |
| 12:03:25–34 | dmesg：卡 4/5/6/7 各 1 条 `KL_XID_KERNEL_EXCEPTION`（`ch=2`） |
| 12:06–12:10 | 4–7 上 4 进程 XCCL 探针：**0/4**（停在 `xccl_probe.py:33` `p8l.cpu()`） |
| 12:11 | 0 号卡单卡算力探针 **通过**（0.09 s） |
| 12:15–12:20 | 挂住的 XCCL 探针自行退出（约 14 分钟）；8 卡回到 `0MiB / 0%` |
| 12:17:12–17 | dmesg：卡 4–7 又各 1 条 Xid（探针退出时，`ch=1`） |
| 12:20–12:24 | 4–7 再跑 preflight：**XCCL 0/4**（设备已坏） |
| 12:24:3x | 0–3 preflight：**全过**（XCCL 4/4 + 算力 4/4），随后起服务 |
| 12:28:3x | **挂死 #2**（0–3，`kernel_0`） |
| 12:35:07 | watchdog 超时 |
| 12:35:19–29 | dmesg：卡 0/1/2/3 各 1 条 Xid（`ch=2`） |
| 12:38–12:42 | 0–3 上的 2 进程 XCCL 探针：**0/2** |
| 13:05–13:07 | 8 张卡各跑算力探针：**0/8**，全部停在 `compute_probe.py:26` 的 `.item()` |

结论：

1. **Xid 是逐卡的**：先坏 4–7，0–3 在 #2 之后才坏；与"换卡无效、跟 rank 序号"的旧结论
   不冲突 —— 旧结论说的是 D2H 挂死跟 rank 走，这里说的是 Xid 落在实际运行的那几张卡上。
2. **挂死本身会留 Xid**，不是只有 `kill -9` 才会。全程没有对 launcher/scheduler 发过 -9。
3. 坏状态的判据是"**任何 D2H 都挂**"，而不是显存/util 异常：
   `xpu-smi` 显示 `0MiB / 0%`、`Processes: None`，但 `p8l.cpu()` / `.item()` 都永久停住。
4. 恢复手段只有节点级重启（`doc/3` §5）；`xpu-smi -r` 在历史上被泄漏的 "in use"
   引用计数挡住，本次未尝试。

## 4. 为什么 DSV4 在同一台机器上能跑

EB5 和 DSV4 的 mHC **概念相同，代码路径不同**：

| | EB5 | DSV4 |
|---|---|---|
| 入口 | `ernie5.py:17` 硬 import `mhc.mhc_pre` / `mhc_post` | `deepseek_v4.py:2542` `hc_pre_torch_impl` |
| pre | `mhc.mhc_pre` → `kernel_0`（split-k）或 `tf32_hc_prenorm_gemm` | 纯 torch：`F.linear(x_flat, hc_fn)` + `rsqrt` |
| post | `mhc.mhc_post` → `mhc_post_tilelang` | 纯 torch：`hc_post_torch_impl` |
| 开关 | 无 torch 分支 | `DEEPGEMM_HC_PRENORM=0`（脚本显式设）+ `x.shape[0] < 1024` 才走 tf32，warmup 3 token 永远走 torch |

另外 `_is_xpu` 在本机是 **False**（`torch.xpu` 存在但 `is_available()==False`），
所以 DSV4 连 `sgl_kernel.mhc_pre` 那条分支也不会进。

**DSV4 跑通证明的是**：`hc_split_sinkhorn` / `hc_combine` / `hc_post` 这套
（插件已 hook 到 `kunlun_ops`/torch）在昆仑上可用；
**没有证明** EB5 的融合 `mhc_pre` / `mhc_post` 可用 —— 后者 DSV4 从未调用过。

## 7. 仍未确认的点

1. **#2 的真凶是 `.contiguous()` 的 strided copy 还是 `xs @ fk` 的 matmul**，
   需要在健康设备上用 `CUDA_LAUNCH_BLOCKING=1` + 单卡复现来区分；
   `EB5_MHC_SINGLE_SPLIT=1` 和 `EB5_MHC_TORCH_REF=1` 分别能把这两段绕开，可作为对照实验。
2. **挂死 → Xid → 半坏**这条链的触发条件仍不清楚：为什么 3 token 的 warmup 会撞上，
   而单卡同形状（token=8）不会。当前只能确认"多 rank + DP attention + 小 token"是高危组合。
3. `xpu-smi -r` 在本次状态下是否可用未测试（需要人工确认，且要等挂住的进程全部退出）。
