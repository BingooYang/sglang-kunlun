# 6. EB5 在线 INT8 量化（昆仑 P800，2026-10-21）

> 结论：**43 层整网在 4 张卡上跑通，输出通顺**（`France → Paris`）。
> BF16 整网在 8 卡上是结构性显存墙（见 §2），INT8 是唯一可行解。
> 运行流程见 `3. eb5模型运行.md` §11，性能债见 `4. 临时D2H与性能债.md`。

## 一、结论速览

| 项 | BF16 | INT8 |
|---|---|---|
| 8L 权重/卡（4 卡） | 28.5–30.0 GB | **15.8 GB（−47%）** |
| 整网权重/卡 | 79.5 GB（8 卡）/ 143 GB（4 卡装不下） | **75.0 GB（4 卡，EP4）** |
| 整网 4 卡 | ❌ | ✅ **4/4 HTTP 200，输出通顺** |
| 8 卡预估 | OOM（差 10–128 MB） | **≈41 GiB/卡**，KV 余量 ≈50 GB |
| 精度 | — | 端到端 **1.19–1.68%**（真实权重） |
| 速度 | 1× | **≈2.5× 慢**（per-token quant + int8 GEMM） |

## 二、为什么必须 INT8（BF16 整网的显存账本）

实测（8 卡、43 层）：

```
权重 74.03 GiB + forward 工作区 16.1 GiB + 非 torch(XCCL/DeepEP) 5.9 GiB + KV 0.4–1.5 GiB ≈ 96 GiB
```

- 首个 forward 时 torch 从 16.7 GiB 空闲涨到只剩 56–106 MiB，随后 64–128 MiB 申请就 OOM
- **KV 池走 `kunlun_ops` 原始分配器，不计入 torch 账本** → `ctx` / `mem-fraction` / `max-total-tokens`
  对 OOM 无效（ctx 32768→8192 后 allocated 仍为 90.12 GiB）
- `chunked-prefill-size` 必须被 `page_size`(1024) 整除 → 预填块压不到 1024 以下
- `max_running_requests` 是**全局值**，必须 ≥ dp_size（8 卡时最小 8）

## 三、可用的 INT8 粒度（重要负结果）

昆仑 `kunlun_ops 0.1.227` **没有可用的 128×128 block-scale INT8 GEMM**：

| 尝试 | 误差 |
|---|---|
| `matmul` + block scale `[n/128,k/128]` | 91% |
| 其它 block 布局 | 24%–1625% |
| `m_grouped_gemm_I8_I8_*` + block scale | **NaN** |
| 同一调用 + per-channel `[E,n,1]` | **0.33%** ✓ |
| `gemm_I8_I8_bf16_nt`（文档 `[g,n,k]` 形态） | `ValueError: unsupported tensor shape` |

→ **只能 per-token 激活 + per-output-channel 权重**；显存收益与 block 方案相同（都是 1 字节/元素）。

粒度对比（同批数据）：per-tensor 2.75% → **per-channel 1.74%** → block-W 1.50% → block-W+A 0.97%。

## 六、已知限制

1. 无 block-scale INT8 GEMM（精度比 block 方案差 0.3–0.8pt）
2. `EB5_INT8_LINEAR_CPU_STAGING=1` 会让 `kv_b_proj` 占位落 CPU，而 EB5 的 `post_load_weights`
   在量化前用它构造 MLA absorb 缓冲 → 首前向 `mat2 is on cpu`；当前把 `kv_b_proj` 排除在暂存外规避
3. `/update_weights_from_tensor` 不支持 INT8 层（per-row scale 不重分片）
4. `Int8MoEMethod.apply` 只实现 standard dispatch，DeepEP 走插件既有 `forward_int8` 分支
5. 性能慢 ~2.5×（未做优化）
6. 精度只验到 GEMM 级 + 输出通顺，未做 KL/MMLU
7. 昆仑实测：`gemm_I8_I8_bf16_nt` 的官方文档形态（`[g,n,k]`）**不可用**，
   实际走的是 `m_grouped_gemm_*` + per-channel scale

## 九、性能实测

固定条件：`--disable-cuda-graph`、`temperature=0`、`ignore_eos=true`、
`tp=8 / dp=8 / ep=8`、`--enable-dp-attention`、`ctx 32768`、`MEM_FRACTION=0.88`、
`MAX_RUNNING_REQUESTS=8`（每个 DP rank 实际 1 条）。

prompt 构造：短输入用 `"The quick brown fox jumps over the lazy dog and keeps running. "` 重复 10 次
（`/tokenize` 校准 = 131 tok）；长输入用 `"In a distributed inference system, ..."` 重复 76 次
（= 2053 tok）。每条请求前置 `[req <uuid>]` 唯一前缀避免 radix prefix cache 命中。
输出长度由 `ignore_eos=true` 固定为 `max_new_tokens`。

| 并发 | 输入 tok | 输出 tok | 平均 TTFT (s) | 平均总延迟 (s) | 单请求 tok/s | 聚合 output tok/s | 聚合 total tok/s | 成功/总数 |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 8 | 131 | 64 | 2.48 | 39.73 | 1.69 | 12.84 | 43.69 | 16/16 |
| 16 | 131 | 64 | 22.38 | 59.58 | 1.69 | 12.86 | 43.66 | 32/32 |
| 32 | 131 | 64 | 62.12 | 99.27 | 1.70 | 12.88 | 43.78 | 64/64 |
| 8 | 2053 | 16 | — | — | — | — | — | 0/16（ragged 分支崩溃） |

> 单请求 tok/s = `(completion_tokens-1)/(总延迟-TTFT)`；聚合值按组墙钟时间计算。
> 并发 16/32 的 TTFT 包含排队时间（`max_running_requests=8` 全局，dp=8 时每 rank 只跑 1 条），
> 因此 22.4 s / 62.1 s 是「2 波 / 4 波」的队列延迟，不是 prefill 变慢。

### 显存 / 利用率峰值（`xpu-smi`，每组约 2 s 采样）

| 组 | 并发 | 显存峰值 MiB | 显存峰值 GiB | util 峰值 |
|---|---:|---:|---:|---:|
| short-c8 | 8 | 80512 | 78.62 | 89% |
| short-c16 | 16 | 81190 | 79.29 | 97% |
| short-c32 | 32 | 81944 | 80.02 | 98% |
| long-c8 | 8 | 93666 | 91.47 | 100% |

> `long-c8` 的 93.7 GB / 100% 是 scheduler 崩溃前后的瞬时值（KV 仍在池里、进程未回收），
> 不作为稳态显存结论。稳态 8–32 并发峰值 **78.6–80.0 GiB**，util **89–98%**。
> 显存构成：INT8 权重 40.83–40.87 GiB/卡 + KV 2,292,736 tok（16.45 GB）+ 工作区，`avail mem=27.22 GB`。

### 长输入（ragged 分支）：不可用，且会打挂整个 scheduler

8 并发 × 2053 tok：**0/8 成功**，客户端全部 300 s 超时；服务端在第一个 prefill 块就崩溃：

```
[10:10:29] Prefill batch, #new-seq: 1, #new-token: 1024, #pending-token: 1054
[10:10:30] Scheduler hit an exception
  nsa_indexer.py:475  _indexer_torch_ref -> self._get_topk_ragged(...)
  nsa_indexer.py:783  _get_topk_ragged    -> kunlun_ops.I8_mqa_logits(q=..., fused_kv_cache=(k_fp8, k_scale), ...)
  kunlun_ops/_deepgemm.py:776 -> xpu_kunlun_ops.dsa_mqa_logits
ValueError: Check torch_tensor.dtype() == CPPTypeToTorchType<T>() failed,
            left operand=unsigned char, right T=int8 create_xops_tensor(Tensor) failed
[10:10:30] Subprocess scheduler_0 (pid=910194) crashed with exit code -3
```

定位：`nsa_indexer.py` 的 paged 分支（短输入/解码走这里）在把 indexer K cache 交给 vendor 算子前
显式做了 `kv_cache_fp8.view(torch.int8)`（同 itemsize、零拷贝，注释写明「buffer 是 uint8(Byte)，
vendor 只收 Char(int8)」）；ragged 分支（>index_topk=2048 的 prefill 走这里）直接用
`get_index_k_continuous()` 返回的 **uint8** buffer，漏了这一步转换，导致 `I8_mqa_logits` 的
模板类型检查失败。同一轮日志里 `topk-ragged:done` 出现 **0 次**，paged 分支正常。

影响：不是单条请求失败，而是 **scheduler 进程退出、8 个 rank 全挂**；之后 HTTP 前端仍返回 200，
请求会一直挂到客户端超时。因此当前 INT8 服务只能服务 ≤2048 tok 的 prompt。

建议修复（一行，未改代码）：`_get_topk_ragged` 里 `k_fp8 = torch.cat(k_fp8_list, dim=0)` 之后
加 `k_fp8 = k_fp8.view(torch.int8)`（零拷贝），与 paged 分支对齐。

### 与 BF16 / 8L 的对比

| 对象 | 单请求解码 | 聚合 output | 备注 |
|---|---:|---:|---|
| **8 卡整网 INT8（本轮）** | **1.69 tok/s** | **12.9 tok/s** @8 并发 | 43 层、ctx 32768、eager |
| 8L INT8（4 卡，§五） | 1.55–1.68 tok/s | ≈6.4 tok/s @4 并发 | 32 new tokens，ctx 8192/0.85 |
| 8L BF16（4 卡，§五） | ≈4.1 tok/s | ≈16.4 tok/s @4 并发 | 32 new tokens |
| BF16 整网 8 卡 | — | — | 权重 79.5 GB/卡 + 首前向 15.7 GB > 96 GB，结构性 OOM |

1. **INT8 整网的单请求解码速度与 8L INT8 子模型几乎相同**（1.69 vs 1.55–1.68 tok/s）。
   层数从 8 增到 43、卡数从 4 增到 8，单请求速度没有变化 → 瓶颈不是权重带宽或层数，
   而是 per-token 量化 + 无 block-scale 的 INT8 GEMM 调度开销（§六.5「慢 ~2.5×」）。
2. 相对 BF16 8L 的 4.1 tok/s，INT8 慢 **2.4–2.5×**，与 §一 的结论一致。
3. **聚合吞吐在 8 并发就饱和**（12.84 → 12.86 → 12.88 tok/s），因为
   `MAX_RUNNING_REQUESTS=8` 是全局值、dp=8 时每个 rank 只能跑 1 条；16/32 并发只是排队
   （TTFT 2.48 → 22.38 → 62.12 s）。要测吞吐上限必须把 `MAX_RUNNING_REQUESTS` 调到 32/64 再跑，
   本轮未做（避免改服务配置）。
