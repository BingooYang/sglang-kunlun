## 3. 尝试过的开关组合与结果

| # | 关键开关 | 结果 | 证据 |
|---|---|---|---|
| A0 | `--disable-cuda-graph`（基线）+ `--deepep-mode normal` | ✅ 4/4 200，稳定 | `logs/eb5_kunlun_20261021_114816.log` |
| A1 | `--cuda-graph-config {"decode":{"backend":"full","max_bs":8,"bs":[1,2,4,8]}}` + `--deepep-mode normal` | ❌ **图被框架强制关掉**，服务仍是 eager | `logs/eb5_kunlun_20261021_115155.log:189` |
| A2 | 同上，但 `--deepep-mode low_latency`（默认）+ `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` | ❌ 捕获进入模型前向，**挂死**（>4 min 不结束） | `logs/eb5_kunlun_20261021_115608.log` |
| A3 | A2 + 去掉 `expandable_segments`（`PYTORCH_CUDA_ALLOC_CONF` 不设） | ❌ 同样挂死 | `logs/p17_20261021_120344_p30110.log` |
| A4 | A3 + `--json-model-override-args {"hc_sinkhorn_iters":1}`（把 sinkhorn 迭代从 20 降到 1） | ❌ 仍挂死，只是**卡在更靠后的 op** | `logs/p17_20261021_120826_p30110.log` |
| A5 | A4 + `--moe-a2a-backend none`（绕过 DeepEP） | ❌ 仍挂死，卡在另一个 op | `logs/p17_20261021_121205_p30110.log` |

**结论 1（框架约束）**：`--deepep-mode normal` 会**无条件**把 decode/prefill 两个 phase 的 graph
都设成 `disabled`，即使命令行显式给了 JSON 配置：

```python
# code/sglang/python/sglang/srt/arg_groups/moe_hook.py:308
if a2a_backend == "deepep":
    ...
    if cfg.deepep_mode == "normal":
        logger.warning("Cuda graph is disabled because deepep_mode=`normal`")
        declare_resolution(server_args, "_handle_a2a_moe",
                           cuda_graph_config=with_phase(cfg.cuda_graph_config,
                                                        Phase.DECODE, backend=Backend.DISABLED))
        declare_resolution(server_args, "_handle_a2a_moe",
                           cuda_graph_config=with_phase(cfg.cuda_graph_config,
                                                        Phase.PREFILL, backend=Backend.DISABLED))
```

服务启动日志里能直接看到这条（`eb5_kunlun_20261021_115155.log:189`），随后 `server_args` dump 里
`cuda_graph_config.decode.backend = 'disabled'`（但 `max_bs` / `bs` 保留，说明 JSON 被解析了、只是
被 `moe_hook` 覆盖）。**所以：想要 decode graph，必须 `--deepep-mode low_latency`。**

**结论 2（捕获参数）**：`max_running_requests=4 / dp=4` 下每 rank 只有 1 条在跑，实际捕获桶就是
`bs=[1]`（日志：`Capture target decode CUDA graph begin. backend=full, num_tokens_per_req=1, bs=[1]`），
显式给 `bs=[1,2,4,8]` 不会多捕桶。要做多桶，得把 `--max-running-requests` 提到 `dp_size × N`。

## 4. 失败点逐条

### F1（已定位，框架行为，非 bug）`deepep_mode=normal` 强制关图

- **现象**：给了 `--cuda-graph-config {"decode":{"backend":"full"}}`，启动后 `cuda_graph={decode=0.00}`。
- **位置**：`sglang/srt/arg_groups/moe_hook.py:308-323`。
- **原因**：DeepEP normal 模式（prefill 用）没有 graph 化的 dispatch 实现，框架直接关两个 phase。
- **是否已修**：不需要修，绕开即可（改 `low_latency`）。
- **影响**：这是「必须 low_latency」的硬前提，而 low_latency 又引出 F3/F4。

### F2（已定位，插件侧风险）low_latency 的 masked MoE dequant 一次非法访存

- **现象**（2026-10-21 11:15，第一次 low_latency + eager 试跑，**与开图无关**）：
  服务 ready 后第一个 warmup 前向，DP3 抛
  ```
  File ".../ep_moe/layer.py", line 1260, in forward_deepgemm_masked_bfp16
      per_token_dequant2d_with_mask(...)
  File ".../kunlun_ops/_xflashinfer_quant.py", line 320
      ret = xpu_flash_ops.dequant2d_per_token(x, scale, y, recv_count, is_absmax, force_sdnn)
  RuntimeError: optimized_ops::dequant2d_per_token failed r=2
  ```
  随后 `CUDA error: an illegal memory access was encountered`，dmesg 记 `KL_XID_KERNEL_EXCEPTION`（dev0）。
- **原因**：`hidden_states` 是 DeepEP LL 量化下发的 **int8**，走 `is_absmax=True` 反量化；该 kernel 在实际
  服务形态下失败（当时设备刚经历过一次崩机，不能排除设备半坏放大）。
- **独立验证**：`.build/p17_dequant_probe.py` 用**真实形态**（`G=128, M=256, N=2048`，int8 x、
  fp32 scale `[G,M,1]`、int32 `recv_count`、bf16 y）单独跑，**4 组全部通过且数值与参考一致**
  （`RESULT: ALL_OK`）。说明 kernel 本身可用，服务里的失败更像**设备状态**或**上游 buffer/stride** 问题。
- **是否已修**：未修（未复现于干净设备上的后续 low_latency 起服务；A2–A5 都过了这一步）。
  后续要复现，建议在 `forward_deepgemm_masked_bfp16` 里加 `EB5_MOE_TRACE=1` 打点（打印
  `hidden_states.shape/stride/masked_m.dtype/recv_count.max()`）后再判。

### F3（**核心阻塞**）整图捕获挂死在模型前向里

- **现象**：`Capture target decode CUDA graph begin. backend=full, num_tokens_per_req=1, bs=[1],
  avail mem=31.84/33.42 GB` 之后**再无输出**，4 个 rank 全部 100% util（显存 ~70.5 GB / 96 GB），
  CPU 每 rank ~100%（累计 CPU 时间持续增长），4 分钟以上不推进。
- **栈（py-spy，三次不同配置分别命中三个不同 op）**：

  A2/A3（20 次 sinkhorn 迭代）：
  ```
  _hc_split_sinkhorn_torch (01_eb_adp/test/eb5_kunlun_adapt.py:599)   # comb / (comb.sum(dim=1)+eps)
  mhc_pre_torch_ref (eb5_kunlun_adapt.py:687)
  _mhc_pre (internal/models/eb5/ernie5.py:3635)
  forward (ernie5.py:3737)
  run_once (runner/decode_cuda_graph_runner.py:1189)
  capture_one (runner_backend/full_cuda_graph_backend.py:144)
  ```

  A4（`hc_sinkhorn_iters=1`，绕过 sinkhorn 后往下走了一层）：
  ```
  _gather_bytes (01_eb_adp/test/eb5_mla_adapt.py:838)
  _mla_gather_kv (eb5_mla_adapt.py:921)
  flash_mla_with_kvcache (eb5_mla_adapt.py:964)
  forward (hooks/layers/attention/deepseek_v4_backend.py:2275)
  _forward_hca (backend.py:369)
  ```

  A5（`--moe-a2a-backend none`，绕过 DeepEP）：
  ```
  rmsnorm (kunlun_ops/_xflashinfer_norm.py:488)
  rmsnorm (sglang_kunlun/kernels/sgl_kernel_kunlun/layernorm.py:35)
  _compress_norm_rope_store_kunlun (sglang_kunlun/kernels/dsv4_torch_shim.py:1158)
  compress_norm_rope_store_bf16 (kernel_ops.py:2643)
  _forward_compress_all_in_one (dsv4/compressor_v2.py:216)
  ```

- **原生栈（关键）**：CPU 不是在等锁，而是在 **driver 的 kernel 下发里自旋**：
  ```
  sched_yield (libc)
  libxpucuda.so ... -> xpu_launch_async (libxpurt.so)
  xpukernel_xpu3::tensor_calc_scalar / xdnn_pytorch::add_scalar / add_tensor
  _hc_split_sinkhorn_torch (eb5_kunlun_adapt.py:599)
  ```
  即 **launch queue 满了**，说明卡上有一个 kernel 一直不结束（设备 100% util），CPU 只是被反压住。
- **不是设备故障**：这几次挂死期间 `dmesg` 在 **dev0–3 上没有新的 KL_XID**（同期 dev4 的 Xid 属于
  4–7 上的另一个任务），进程退出后显存自动回到 0 MiB。
- **不是单个 op 的问题**（见 §5）：同一批 op 单独 capture+replay 全部通过。
- **推断**：挂死与「**整图（≈ 数千个节点）+ 4 rank 同步**」有关，而不是某个算子。最可能的两类原因：
  1. **DeepEP low_latency / XCCL 的 rank 间锁步**：捕获时 4 个 rank 各跑各的 Python，进度会错开
     一到多层；DeepEP LL 的 dispatch 是**设备侧自旋等 peer** 的 kernel，一旦错位就可能长时间等待，
     把该卡的 launch queue 打满 → 层层反压。A5 去掉 DeepEP 后仍然挂，说明 XCCL/TP 集合通信或
     XPU 捕获本身也在其中起作用。
  2. **XPU 整图捕获的规模上限/驱动问题**：`XMLIR_FORCE_USE_XPU_GRAPH=1` 下，捕获几千个节点时
     驱动侧卡住（每个 rank 命中的 op 都不同，像是“各自卡在自己那条 capture 流上”）。
- **是否已修**：❌ 未修（这是本次任务的主要遗留）。

### F4（已定位，非阻塞但影响判据）捕获桶只有 `bs=1`

- 每 DP rank 只有 1 条在跑（`max_running_requests=4 / dp=4`），所以 decode 图只有 `bs=1` 一个桶。
- 判据里的「bs 桶按 1/2/4/8」需要把 `--max-running-requests` 放到 16（dp4 × 4）才可能出现多桶。

脚本（都在 `.build/`，不属于仓库代码）：

## 6. 插件侧改动

### 6.1 已落地的改动

**没有改 `sglang_kunlun/` 或 `01_eb_adp/test/` 下的任何插件源码。** 本轮只新增了实验性辅助脚本
（都在 `.build/`，不进仓库、不影响 4–7 的任务）：

| 文件 | 作用 |
|---|---|
| `.build/p17_launch.sh` | 与 `run_eb5_kunlun.sh` 等价的启动器，但 ① 允许用 `GRAPH_ARGS` 完全替换图参数；② 允许 `ALLOC_CONF=` 覆盖 `PYTORCH_CUDA_ALLOC_CONF`。只用于 0–3 实验 |
| `.build/p17_bench.py` | 4 并发 × N token 基准（TTFT / 总延迟 / 单请求 tok/s / 聚合 tok/s / 输出文本） |
| `.build/p17_capture_probe.py` / `p17_op_graph_probe.py` / `p17_xccl_graph_probe.py` / `p17_dequant_probe.py` | 把 §5 的对照实验固化成可复跑脚本 |

`run_eb5_kunlun.sh` 仍然写死 `--disable-cuda-graph`，**没有改**（4–7 的任务在用同一个脚本）。
要开图请用 `.build/p17_launch.sh`，或把 `--cuda-graph-config` 塞进 `EXTRA_ARGS`
（注意：`deepep_mode=normal` 下会被框架覆盖，见 F1）。

### 6.2 建议的插件侧改法（下一步，未实施）

1. **捕获期给 DeepEP dispatch 加 rank 锁步**（对应 F3 推断 1）
   - 落点：`sglang_kunlun/...` 或 fork 的 `DeepEPCudaGraphRunnerAdapter`，在 `capture()` 路径上
     于每次 dispatch 前后插入 `torch.distributed.barrier()`（仅在 capture 模式；
     `get_is_capture_mode()` 可取到），把 4 个 rank 重新对齐。
   - 预期：若挂死消失，则定义域确认在 DeepEP/XCCL 的捕获锁步。
2. **捕获期把 DeepEP dispatch/combine 换成「只记录形状、不做通信」的 stub**
   - 落点：`sglang_kunlun/hooks/layers/moe/ep_moe/layer.py` 的 `forward_deepgemm_masked*` /
     `run_moe_core`，capture 模式下走本地 GEMM（`m_grouped_gemm_*_masked_v3` 保留），跳过
     `deepep` 的 FIFO 通信；replay 时由真实 graph 执行。
   - 风险：dispatch 结果（`recv_count`/`masked_m`）在捕获时是假的，graph replay 会复用捕获时的
     **静态 masked_m**——只有所有 rank 每步 token 数完全一致时才正确。**不建议先走这条**。
3. **先做最小验证**：`--dp-size 1`（关 DP attention）跑一次捕获。
   - 若通 → 阻塞点在 DP/DeepEP 的 rank 协同（含 `dp_attn.py` 的 all_gather），
     再按 1) 处理；若还不通 → 落在 XPU 整图捕获规模上，转 4)。
4. **换后端**：`--cuda-graph-backend-decode breakable`（分段捕获，图规模小得多）。
   fork 的 `BreakableCudaGraphBackend` 已在，未在昆仑上验证过。

> **2026-10-21 13:55 状态更新**：第 3 条（单卡最小验证）已在 INT8 路径做完并通过 —— 单卡整图捕获、replay、出 token 全通（§8.3）；
> 随后发现阻塞点不在「整图规模」而在多 rank（DeepEP 初始化 + ep=2 的 dequant 缺陷，§8.4/§8.5）。
> 真正落地的插件改动只有一处：DSA decode-graph metadata 的外层 `kernel[grid]` 兜底（§8.3.3、§8.6）。

## 8. 隔离实验（INT8 单卡 → 多 rank；breakable / DeepEP）

> 2026-10-21 13:00–14:00。目的：把「整图捕获挂死」拆成 ①DP/DeepEP 多 rank 锁步 还是
> ②XPU 整图捕获规模本身。**只用了 0–3 号卡**，4–7 上的 MTP 服务（30120）全程未触碰。
>
> 一句话结论：**XPU 整图捕获本身没问题** —— 8L/INT8/单卡（ep=1、不走 DeepEP、无 DP 通信）
> 的 decode 整图 **4.3–4.5 s 捕获成功，并且 replay 能正常出 token**（吞吐 +12–17%、TTFT −39%）。
> 挡路的是**多 rank**：BF16 2 卡在 ep=2 的 masked dequant 上必炸（eager 也炸），
> INT8 2/4 卡则卡在 **DeepEP buffer 初始化 / load 收尾**。

### 8.0 结论表

| 实验 | 形态 | 结果 | 判据/关键数字 |
|---|---|---|---|
| A0 | BF16 8L，**单卡** tp1/dp1/ep1 | ❌ **显存不可行** | 权重 `mem usage=95.44 GB`，加载后 `avail mem=0.38 GB`（8L 总权重 115 GB，BF16 按卡摊 26.5 GB 是 **tp4** 的数） |
| A2-eager | BF16 8L，2 卡 tp2/dp2/ep2 + low_latency，**eager** | ❌ 崩 | `RuntimeError: optimized_ops::dequant2d_per_token failed r=2` → `CUDA error: wait for noc idle timeout`（dev 上 `KL_XID_KERNEL_EXCEPTION`） |
| A2-graph | 同上 + decode graph | ❌ 崩（**不是挂死**） | `Exception: Capture cuda graph failed: ... dequant2d_per_token failed r=2` + dev0 `KL_XID`（52:00） |
| **A'** | **INT8** 8L，**单卡** tp1/dp1/ep1，`--moe-a2a-backend none` | ✅ **通过** | 捕获 **4.33 / 4.47 / 4.49 s**（三次），`bs=[1,2]`；replay 需两处修复（见 §8.3.3）；graph 3.80–3.86 tok/s/req vs eager 3.39（**+12–14%**），TTFT 0.45 vs 0.74 s（**−39%**） |

| C' | INT8 8L，4 卡 tp4/dp4/ep4 + low_latency + **breakable** decode | ⏱ 超时放弃 | 卡在 **DeepEP buffer v2 初始化** `deep_ep/buffer_v2.py:101 all_gather_object`，4 卡 100% util、6 min 无进展 |

### 8.1 为什么全部改用 INT8（A0 的硬数字）

BF16 8L 的 **总权重是 115 GB**（doc/3 §11.2：`du -shL` = 115 GB），
「26.5 GB/卡」是 **tp=4** 摊完的结果。单卡 tp1 实测：

```
logs/p17_20261021_125231_p30130.log
[12:53:21] Load weight end. elapsed=23.82 s, type=ErnieMlaHcaForCausalLM,
           avail mem=0.38 GB, mem usage=95.44 GB.
```

95.44 GB / 96 GB，连 KV pool 都放不下（`mem-fraction` 提到 0.995 也没用），
所以「单卡 + BF16」这条路从显存上就不成立 —— 这也是本轮改用 INT8 的唯一原因。
INT8（`blockwise_int8`，per-output-channel 权重 + per-token 激活）单卡权重 **48.48 GB**，
`avail mem=47.34 GB`、KV `max_total_num_tokens=10,945,280`。

#### 8.3.3 replay 路径上的两个真实阻塞（都已定位并给出修法）

1. **`fused_dsa_decode_metadata` 的 `kernel[grid]`**（只在 graph replay 路径被调用）
   ```
   decode_cuda_graph_runner.execute → load_batch → init_forward_metadata_out_graph
   → dsa_backend.py:1588 _apply_cuda_graph_metadata
   → kernels/ops/attention/dsa_kpool_metadata/decode.py:197 fused_dsa_decode_metadata
   TypeError: 'function' object is not subscriptable
   ```
   插件里已有 torch 等价实现 `fused_dsa_decode_metadata_torch`（`kernel_ops.py:2806`），
   但只注册在 **内层 kernel** `_fused_dsa_decode_metadata_kernel` 上；外层仍在 `[grid]` 启动，
   于是 `'function' object is not subscriptable`。→ 修法见 §8.6（`EB5_DSA_META_GRAPH_PATCH=1`）。
2. **overlap scheduler 的事件等待**：补上 1）之后，启动 warmup 第一轮报
   ```
   scheduler.py:1947 _apply_war_barrier → torch/cuda/streams.py:203 wait
   torch.AcceleratorError: CUDA error: invalid argument
   ```
   → `--disable-overlap-schedule` 绕开（框架自带开关，无需改代码）。两处都处理后 `health=200`。

1. **先把「INT8 + 单卡 graph」固化成可回归用例**（已跑通，成本最低）：
   `A2A_BACKEND=none` + `EB5_DSA_META_GRAPH_PATCH=1` + `--disable-overlap-schedule`，

3. **ep=2 的 `dequant2d_per_token` 必现失败**单独开卡：把 `masked_m` 的真实值/形状打出来

   stride 约定；在此之前不要用 2 卡做任何图实验。
4. breakable 后端要等 2 修好后再复测（配置层已确认可用，只关 prefill 图）。
5. 整网（43 层）开图前，先补 **graph vs eager 的 logits 对比**（8L 乱码输出无法判正确性）。

## 9. 运维注意事项（本轮踩到的）

1. **`kill -9` 卡在 XPU 调用里的进程会把卡打成半坏态**。本轮为图省事 `kill -9` 了一个卡在
   tensor repr（内部 D2H）里的探针，之后该卡 `torch.cuda.init()` 和 alloc 都正常，
   但**任何真实 kernel（`sum`/`div`）永久挂住**——正是 doc/3「最重要的一条」。
   处理：`xpu-smi -fr -i 0,1,2,3`（约 30 s 恢复），然后必须重跑 preflight 的**算力探针**确认。
   正常停服请只 `kill -TERM <launcher>`；launcher 卡在 waitpid 时，只对**纯 CPU 的
   tokenizer/detokenizer worker** 用 `-9`（与 `stop_kunlun.sh` 的分级策略一致）。
2. **端口**：30110 的 dist 端口是 30343（`ZMQ_TCP_PORT_DELTA = 233`），换端口时两边一起看。
3. **同机他人任务**：本轮 4–7 上一直有另一个任务（30120），期间它崩过一次（dev4 Xid），
   该 Xid **不属于** 0–3；判读 dmesg 时必须按 PCI 地址（52:00 / 55:00 / 63:00 / 66:00 才是 0–3）。

## 11. 多 rank 捕获：去掉 DeepEP 的对照 + `breakable` 复测（2026-10-21 14:00–14:40）

§8 把单卡打通之后，剩下的问题只有一个：**为什么 4 个 rank 的整图捕获会挂**。
本节把 DeepEP 和图后端这两个变量分别摘掉，结论是**两个都不解决**——多 rank 的
首个 XCCL all-gather 在捕获期没有被所有 rank 对称地发出。

### 11.1 对照 1：4 卡 INT8，`ep=1` + `--moe-a2a-backend none`（不创建 DeepEP）

```bash
EB5_GPUS=0,1,2,3 MAX_RUNNING_REQUESTS=4 MEM_FRACTION=0.85 \
GRAPH_ARGS="--cuda-graph-backend-decode full --cuda-graph-max-bs-decode 4" \
EXTRA_ARGS="--quantization blockwise_int8 --moe-a2a-backend none --ep-size 1 --disable-overlap-schedule" \
bash tool/run_eb5_graph.sh models/hf_checkpoint-48800-8L 30158
```

日志 `logs/eb5_kunlun_20261021_135957.log`：

```
[14:00:33 DP0 TP0] Load weight begin. avail mem=95.82 GB      （4 个 rank 对称）
[14:01:09 DP0..DP3] Capture target decode CUDA graph begin. backend=full, bs=[1], avail mem=37.18 GB
（此后无任何输出；4 卡 100% util、65.4 GB 滞留 11 分钟，手动 kill）
```

**结论**：没有 DeepEP 也能走到捕获，但**照样挂**。说明 §8.5 里"卡在 DeepEP 初始化"
只是第一个路障，摘掉它后面还有一个独立的捕获期挂死。

### 11.2 对照 2：4 卡 INT8，`breakable` decode 后端（同样 `ep=1`）

```bash
GRAPH_ARGS="--cuda-graph-backend-decode breakable --cuda-graph-max-bs-decode 4"
# 其余同上，port 30159
```

日志 `logs/eb5_kunlun_20261021_140523.log`：

```
[14:06:34 DP0..DP3] Capture target decode CUDA graph begin. backend=breakable, bs=[1], avail mem=37.18 GB
[14:17:35 rank1] Watchdog caught collective operation timeout:
                 WorkXCCL(SeqNum=1, OpType=_ALLGATHER...)  [PG ID 2 PG GUID 3 (tp:device)]
[14:17:35 rank2/rank3] 同上
[14:26:40] Received sigquit from a child process → kill_process_tree
```

**结论**：分段捕获不改变结论；而且看门狗给出的信息很关键——
**超时的是该通信组上的第 1 个集合通信（`SeqNum=1`），类型 `_ALLGATHER`**，
也就是说捕获刚开始就有一个 all-gather 只有部分 rank 发出/完成。
rank 0 没有报同样的超时，说明它当时停在别的地方（不是同一个 all-gather），
即 **4 个 rank 在捕获期的执行序列不一致**。

### 11.3 归因（⚠️ 已被 §11.6 用 trace + gdb 证据修正，保留作排查过程记录）

| 假设 | 证据 | 结论 |
|---|---|---|
| 是 DeepEP 的问题 | 摘掉 DeepEP（`ep=1`、`moe-a2a none`）后仍然挂 | ❌ 排除 |
| 是整图规模太大 | `breakable` 分段捕获同样挂 | ❌ 排除 |
| 是单算子不支持捕获 | §5 已证明热路径 op 与 4-rank all_gather 单独 capture+replay 均通过 | ❌ 排除 |
| **多 rank 在捕获期执行序列不一致** | 看门狗：`_ALLGATHER` `SeqNum=1` 只有部分 rank 超时；rank 0 行为不同 | ✅ 最可能 |

候选分歧点（按可能性排序）：
1. DP attention 的每步 `all_gather`（token 数/bs 同步）在捕获时被某个 rank 跳过
   ——例如 `bs=0` 的 rank 走 early-return；
2. `mHC` / indexer 里按 host 侧取值（`.cpu()`、`item()`）分支，捕获期各 rank 取到的值不同；
3. 捕获是**逐 rank 串行**进入的（4 个 rank 的 `begin` 时间戳相同但内部阶段未必），
   早到的 rank 先发 collective，晚到的 rank 还在建图。

### 11.4 下一步（可执行）

1. **在捕获期给 DP attention 的 all-gather 前后加 rank 锁步**（`torch.distributed.barrier()`，
   仅 `is_capture_mode()` 时生效，env 开关 `EB5_GRAPH_CAPTURE_BARRIER=1`，默认关）；
   若挂死消失 → 归因确认，再逐步缩小到具体是哪个 collective。
2. **给 4 个 rank 打点**（每个 collective 前打印 `dp_rank + op + seq`），拿到第一个
   "只有部分 rank 打印"的位置；这比 barrier 更能定位分歧点。
3. 分歧若在 `bs=0` 的 early-return，就在捕获期把 `bs` 统一钳到 ≥1（捕获用的是假 batch，
   不需要真实请求）。

### 11.6 归因修正（15:00 之后的新证据）

§11.3 的「rank 执行序列不一致」判断**不成立**，这里用两组硬证据改掉。

**(a) 集合通信 trace（`EB5_COLLECTIVE_TRACE=1`，四个 rank 逐条一致）**

```
barrier(1) exit → all_reduce(1) exit → all_reduce(2) exit → broadcast(1) exit
→ broadcast(2) exit → all_reduce(3) exit → barrier(2) exit
→ all_gather_into_tensor(1) [(4,4096)bf16 ← (1,4096)] exit
→ all_reduce(4) [(4,4096)bf16] exit        ← 之后没有任何通信
```

四个 rank 的 9 条 enter/exit 完全对齐（9 exits / 9 enters）。**捕获期的集合通信
都发出了、host 侧也都返回了**，不存在某个 rank 少发或走了不同分支。

**(b) gdb 主线程栈（捕获挂住时 attach）**

```
sched_yield ← xpu_launch_async ← xpukernel_xpu::memcpy_1d ← xpu::api::copy<int8>
  ← torch_xmlir::copy_d2d ← CUDANativeFunctions::copy_ ← at::copy_
```

捕获期最后一条 `copy_` trace（只有 enter、没有 exit）：

```
dst=(1, 4) src=(1, 4) site=ernie5.py:3737 < ernie5.py:3635 < eb5_kunlun_adapt.py:698
```

即插件 mHC pre 的 `post_mix.copy_(post)`（`01_eb_adp/test/eb5_kunlun_adapt.py:698`）。

**(c) 但这个 copy 不是根因**

同样的 `post_mix.copy_(post)`（同样 (1,4)）在**单卡 INT8 捕获里跑通了**（§8.3，
整图 4.3–4.5 s 捕获成功）。所以：
* 不是「(1,4) 的 copy_ 不能进图」；
* 更可能是**设备队列已经被前面某个捕获的集合通信堵死**，主线程只是恰好停在下一个
  会阻塞的 `xpu_launch_async` 上——watchdog 报的 `_ALLGATHER SeqNum=1` 超时
  （设备侧完成检测）与这个解释一致。

**(d) 单独的最小复现脚本没有跑通（结论不采纳）**

写了 `.build/p19_graph_xccl_probe.py`（4 rank：eager 预热 → 捕获 → replay → sync），
但**它的 eager 预热阶段就挂**；同一个 `xccl_probe.py` 用 4 rank 跑（不是 8 rank）
也只有一个 rank 打印 `all_reduce ok`、其余超时。也就是说这套独立脚本的进程组/设备
绑定方式与 sglang 内部不一致，**不能用它证明或否定“XCCL 能否进图”**，本节结论只
以 §11.6(a)(b) 的服务内证据为准。

### 11.7 结论与建议

| 项 | 结论 |
|---|---|
| 单卡（tp1/dp1/ep1，INT8） | ✅ 整图捕获 + replay 可用，+12–17% 吞吐、TTFT −39%（§8.3） |
| 多 rank（tp4/dp4，含/不含 DeepEP） | ❌ 捕获期挂死；集合通信 host 侧全部返回，设备侧 watchdog 超时 |
| `breakable` 后端 | ❌ 同样挂死（不是图规模问题） |
| 判断 | **XCCL 集合通信在 graph capture 下的设备侧完成性有问题**，需要厂商侧确认；EB5 侧无解 |
| 建议 | 多卡继续用 eager（现状可用）；单卡场景（tp1）可以开图。若要推多卡图，先拿 §11.6(a)(b) 的证据找 KLX XCCL 团队确认 capture 支持，再谈 stub/锁步方案 |

## 12. 多 rank 继续攻坚（19:00–19:45）：环境、拓扑、通信位置、rank 同步全部排除

结论先行：**以上四类修法都没有让多 rank 捕获通过**，而且这轮的证据把问题收敛成一个很窄的
现象——**rank 0 先卡住，其余 rank 在 `_ALLGATHER_BASE` 上等它**。

### 12.1 环境变量扫描（每项一次完整起服务，判据 `Capture ... end` + `ready to roll`）

| 变量 | 结果 |
|---|---|
| `CUDA_GRAPH_OPTIMIZE_STREAM=0` | TIMEOUT |
| `XMLIR_FORCE_USE_XPU_GRAPH=0` | TIMEOUT |
| 两者都关 | TIMEOUT |
| `TORCH_XCCL_AVOID_RECORD_STREAMS=1` | TIMEOUT |
| `XMLIR_XCCL_USE_ASYNC_OP=1` | TIMEOUT |

脚本 `.build/p20_sweep.py` / `p20_sweep2.py`，汇总 `logs/p20_sweep*_summary.txt`。

### 12.2 拓扑绕开：不可行

想用 `tp=1 / dp=4`（attn_tp=1，且没有 TP 分片，理论上可以少一次 DP gather）绕开，
框架在 `arg_groups/parallel_hook.py:193` 直接拒绝：

```
assert cfg.tp_size % cfg.dp_size == 0   # 1 % 4 != 0
```

而 EB5 要求 `attn_tp_size == 1`（`ernie5.py:1080`），dp attention 下 `attn_tp = tp / dp`，
所以**唯一合法拓扑就是 tp == dp == 卡数**，DP gather 一定存在。

### 12.3 把通信挪出图：机制可用，但没解决

fork 的 `BreakableCudaGraphBackend` 自带 `eager_on_graph`：捕获时「结束当前图段 → 立即执行 →
开新图段」，replay 时在段之间重跑。用它包住 EB5 每层的三个 DP 通信：

```python
# sglang_kunlun/hooks/models/eb5_breakable_comm.py（EB5_BREAKABLE_EAGER_COMM=1）
for name in ("dp_gather_partial", "dp_gather_replicate", "dp_scatter"):
    setattr(dp_attention, name, eager_on_graph(True)(getattr(dp_attention, name)))
```

（`ernie5.py:3767/3776` 处的 dense/MoE FFN 前 gather、后 scatter。）

结果：仍然 TIMEOUT；而且 `EB5_EAGER_COMM_DEBUG=1` 的断点打印一次都没出现，
说明捕获**在到达第一个 `eager_on_graph` 包装的调用之前就已经卡住**。

### 12.4 加 rank 同步：捕获能一起进，但只有一半 rank 在动

在 `DecodeCudaGraphRunner.capture` 前后加 `dist.barrier()`（`EB5_GRAPH_CAPTURE_BARRIER=1`）：

- 四个 rank 现在**同一秒**进 `Capture target decode CUDA graph begin`（此前也基本同秒）
- 但 2 分钟后：**卡 0/1 利用率 0%、卡 2/3 100%**，`Capture ... end` 始终不出现

即：同步进捕获并没有让执行序列同步，rank 之间还是分叉。

### 12.5 决定性证据：rank 0 先卡在设备侧，其他 rank 等它

把看门狗超时压到 120 s（`TORCH_XCCL_DEFAUTL_PG_TIMEOUT_MILSEC=120000`）后：

```
[Rank 1/2/3] Watchdog caught collective operation timeout:
  WorkXCCL(SeqNum=1, OpType=_ALLGATHER_BASE, NumelIn=4096, NumelOut=16384, Timeout(ms)=120000)
```

- `NumelIn=4096 / NumelOut=16384` 正是 `(1,4096) → (4,4096)` 的 DP gather（每 rank 一个 token）
- **只有 rank 1/2/3 超时，rank 0 没有** → rank 0 根本没发出这个 all-gather

同时 gdb 抓 rank 0 的主线程：

```
sched_yield ← xpu_launch_async ← memcpy_1d ← copy_d2d_dtype ← Tensor.copy_   （捕获中）
```

而对照实验里**单卡**同代码捕获期执行了 **25,909 次 `copy_`** 依然 4.3 s 捕获成功
（`logs/ct_30216`），所以 memcpy 本身可捕获；rank 0 的 memcpy 是在等一个已经被堵死的设备队列。

**当前定性**：rank 0 在捕获期间先有一个设备侧操作不完成 → 队列堵死 → 它不再发出
`_ALLGATHER_BASE` → 其余三个 rank 在该集合通信上等到看门狗超时。至于 rank 0 卡住的那个
设备侧操作是什么，主机栈只能看到「下一个 launch 阻塞在 memcpy」，需要在设备侧
（等 KLX 的 XCCL / xpurt 支持）继续定位。

### 12.6 结论

| 项 | 状态 |
|---|---|
| 单卡 tp1/dp1（INT8） | ✅ 图可用，+12–17% 吞吐、TTFT −39% |
| 多卡 tp4/dp4（任何后端 / 任何已试 env / 通信移出图 / 捕获前同步） | ❌ 仍挂 |
| 归因 | rank 0 设备侧先卡 → 其余 rank 在 `_ALLGATHER_BASE` 上超时；主机侧已排除「集合通信不能进图」的简单解释 |
| 建议 | 多卡继续 eager；把 §11.6 + §12.5 的证据（含 `NumelIn/NumelOut`、rank 0 不参与、单卡 25,909 次 copy 对照）提交 KLX XCCL/xpurt 团队 |
