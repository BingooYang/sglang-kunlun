# 8. EB5 8L MTP（NextN / 投机解码）适配（2026-10-21，cards 4–7）

> 目标：在**只用 4,5,6,7** 的前提下，给 8 层子模型（`models/hf_checkpoint-48800-8L`）
> 打开 EB5 自带的 MTP（NextN / EAGLE 投机解码），并把相关问题独立记录在本文件。
>
> 结论先行：**MTP 已启用成功**——4 并发 4/4 HTTP 200，`spec_accept_length` /
> `spec_accept_rate` / `spec_verify_calls_total` 三类指标都有数；端到端吞吐
> **11.2–11.8 tok/s vs 不投机 8.6–8.8 tok/s（1.31–1.36×）**。
> 但**接受率 ≈ 1.0 长度（≈1% 的步会多中一个 token）**，因为 8L 是**截断模型**
> （输出本身就是乱码），MTP 头是按 43 层隐状态训练的，对不上是**预期行为**。
> 因此这 1.3× **不是** draft 命中带来的收益（见 §5 的分解）。
>
> 运行流程与踩坑归类见 `3. eb5模型运行.md` / `5. EB5 8L 问题归类与修复索引.md`。

## 1. MTP/nextn 在 EB5 里的入口

| 环节 | 位置 | 说明 |
|---|---|---|
| 目标侧声明 | `ernie5.py:4542` `ErnieMlaHcaForCausalLM.nextn_architecture = "ErnieMlaHcaForCausalLMNextN"`，`nextn_expected_use_mla = False` | 8L 的 config 是 `use_mla=false` + `experimental_attention_variant=dsv4_hybrid`，先被 `_alias_eb5_generic_arch` 改写成 `ErnieMlaHcaForCausalLM`，再命中这个 entry |
| 探测 | `runtime_patch.py:50 _eb5_nextn_support()` | 只读 `EntryClass[*]` 的两个属性，不 import 模型栈 |
| draft config 改写 | `runtime_patch.py:260 _config_draft_model_with_eb5_nextn()`（hook 注册在 `:1265`） | `architectures[0]` → NextN arch；`num_nextn_predict_layers=1`；`is_hybrid_swa=False`；把 `hybrid_mla_*` 提升成 draft 的顶层 MLA 维度 |
| draft 模型 | `ernie5_nextn.py:ErnieMlaHcaForCausalLMNextN` → `EB5ModelNextN` | `enorm/hnorm + e_proj/h_proj`（mHC 开启时走 split 版） + **一层** `EB5DecoderLayer(is_nextn=True)` + `shared_head.norm` |
| draft 权重加载 | `ernie5.py::build_eb5_weight_handlers(is_nextn=True)` | `nextn_layer_id = config.num_hidden_layers`；checkpoint 里的 `model.layers.<N>.*` 映射到运行时 `model.decoder.*`；`transform_layer.*` 前缀被剥掉 |
| draft lm_head | 同上 + `eagle_worker_v2.init_lm_head` | `mtp_shared_last_layer=true` → draft 不自带 lm_head，`load_lm_head_from_target=True`，embed/lm_head 直接用 target 的（`set_embed_and_head`） |
| draft 注意力后端 | `runtime_patch.py:616` `eb5_dsa_draft` → `dsa_full.build_eb5_dsa_draft_backend` | 强制 page=64 + 构造期 `force_dsa_config`，与 target 的 full-MLA 层共用 sink-aware sparse 栈 |
| draft KV 池 | `mla_hca/pool_patch.py::_patch_build_mla_kv_pool`（`_nextn_draft_dsa_mode`） | MTP 层是 full-MLA 层，所以池 = **page-64 的 `DSATokenToKVPool`**（`index_topk>0` → 带 index-k cache），大小按 target 的 `max_total_num_tokens` 放大到能被 256 页分配器覆盖 |

一句话：**EB5 的 MTP 就是「拿同一个 checkpoint 的第 `num_hidden_layers` 层当 draft」**，
和 DeepSeek 的 `model.decoder.*` 命名不同，EB5 的权重在 ckpt 里叫
`model.layers.<N>.*`（N = 目标层数），由 loader 改名到 `model.decoder.*`。

## 2. 权重来源：8L 子模型里没有 MTP，需要单独取

`build_submodel.py` 只保留 `model.layers.0..n-1`，MTP 层（整网的 `model.layers.43.*`）
被一起裁掉：

```bash
$ grep -o '"mtp\.[^"]*"' models/hf_checkpoint-48800-8L/model.safetensors.index.json | head
# （空）
$ python3 -c "import json;wm=json.load(open('models/hf_checkpoint-48800-8L/model.safetensors.index.json'))['weight_map'];print(len(wm), sum('layers.43.' in k for k in wm))"
11050 0
```

整网里 MTP 层的**真实名字**是 `model.layers.43.*`（不是 `mtp.*`；43 = `num_hidden_layers`，
`compress_ratios` 末尾多出来的那个 `-2` 就是它）：

```bash
$ python3 -c "import json;wm=json.load(open('models/hf_checkpoint-48800/model.safetensors.index.json'))['weight_map'];ks=[k for k in wm if k.startswith('model.layers.43.')];print(len(ks));print('\n'.join(sorted(k for k in ks if '.experts.' not in k)[:8]))"
1583
model.layers.43.block_sparse_moe.e_score_correction_bias
model.layers.43.block_sparse_moe.gate.weight
model.layers.43.e_proj.weight
model.layers.43.enorm.weight
model.layers.43.h_proj.weight
model.layers.43.hnorm.weight
model.layers.43.shared_head.norm.weight
model.layers.43.self_attn.core_attention.indexer.wk.weight
```

1583 = 1536 个 routed-expert 张量 + 47 个其余（`e_proj/h_proj/enorm/hnorm/shared_head.norm`、
`self_attn.*`、`transformer_layer.*_hyper_connection.*`、`core_attention.indexer.*`）。

**新工具** `tool/build_mtp_draft.py` 把这些张量**软链**成一个独立 draft 目录
（不改名、不拷贝，零额外空间）：

```bash
python3 code/sglang-kunlun/01_eb_adp/tool/build_mtp_draft.py \
  --src models/hf_checkpoint-48800 \
  --dst models/hf_checkpoint-48800-mtp
# -> mtp_layer=43 keys=1583 (routed-expert=1536) shards=193 read=19.6 GB
```

为什么 draft 目录的 `num_hidden_layers` **必须保持 43**（而不是 8）：

* loader 用 `nextn_layer_id = config.num_hidden_layers` 找权重，所以 draft config 的
  `num_hidden_layers` 必须等于 **MTP 在 checkpoint 里的下标**（43）；
* `build_attn_plan` 要求 `compress_ratios[num_hidden_layers] == -2`，整网 config 的
  44 长列表正好满足（`plan[43] = -2`）；
* draft 的 KV 池层数不吃 `num_hidden_layers`：`layer_setup._compute_model_num_layers`
  对 draft worker 走 `num_stages/num_nextn_predict_layers` → **1 层**。

（若想让 MTP 张量叫 `model.layers.8.*`，就必须**重写 safetensors 里的张量名**
（~13 GB 落盘），本工具故意不做。）

## 4. 失败点清单（op / 栈 / 原因 / 是否已修）

### 4.1 draft KV 池走了错的分支（已修，插件侧）

```
File ".../mem_cache/kv_cache_configurator.py", line 1411, in _build_oot_mla_kv_pool
    token_to_kv_pool = PoolCls(
TypeError: MLATokenToKVPool.__init__() got an unexpected keyword argument 'index_head_dim'
```

* **原因（B 类：插件 ↔ fork API 漂移）**：EB5 早就为 MTP draft 写好了
  `_patch_build_mla_kv_pool`（page-64 `DSATokenToKVPool` + index-k cache），但它挂在
  `KVCacheConfigurator._build_mla_kv_pool` 上；而 fork 把池构造拆成了
  `_build_oot_{mla,dsa}_kv_pool`，**out-of-tree 平台（昆仑）先走 `is_out_of_tree()` 分支**，
  于是 hook 永不触发，落到上游 `_build_oot_mla_kv_pool`——那里无条件给
  `MLATokenToKVPool` 传 `index_head_dim`，而该类没有这个形参。
* **修法**（`code/sglang/python/sglang/srt/internal/layers/attention/mla_hca/pool_patch.py`）：
  同一个 hook 同时注册到两个构造函数上

```python
    for _mla_pool_builder in ("_build_mla_kv_pool", "_build_oot_mla_kv_pool"):
        HookRegistry.register(
            "sglang.srt.mem_cache.kv_cache_configurator.KVCacheConfigurator."
            + _mla_pool_builder,
            _patch_build_mla_kv_pool,
            HookType.AROUND,
        )
```

  该 hook 只对 `is_draft_worker and arch == ErnieMlaHcaForCausalLMNextN` 生效，
  target 与其它模型零影响。
* **遗留（未修，非本任务路径）**：`_build_oot_mla_kv_pool` 自己仍会把 `index_head_dim`
  （即使是 `None`）传给 `MLATokenToKVPool`，**任何** out-of-tree 的 DSA/MLA draft 只要
  走到这条分支都会炸同样的错。要么给 `MLATokenToKVPool.__init__` 加形参（但那会**静默**
  丢掉 index-k cache，对真 DSA 是错的），要么在 fork 侧把 kwarg 收进
  `use_dsa/override_kv_cache_dim`——留给 fork 决定。

### 4.2 `--moe-a2a-backend none` + `--ep-size 4` 直接把 target prefill 挂死（非代码 bug，参数组合不可用）

* 现象：首个 prefill（warmup 7 token）进去就不返回，300 s watchdog；
  py-spy（自动 dump）主线程停在
  `mhc_pre_torch_ref → _hc_split_sinkhorn_torch → torch.sum`，
  且是 `xpu_launch_async` 里等设备（即**前一个 kernel 没结束**，队列堵在 launch 上），
  4 张卡全部 100% util。
* 收尾（SIGQUIT）时留了 `KL_XID_KERNEL_EXCEPTION`（PCI 0000:9a:00，`FW cmd[0x2d] polling timeout`），
  之后 4 张卡进入"看着 0MiB、但 XCCL 探针 0/4"的半坏态（doc/5 A1），
  `xpu-smi -fr -i 4,5,6,7` 复位后 preflight 立刻恢复（XCCL 4/4、算力 4/4）。
* 结论：**EP=4 时必须用 `deepep`**；`none` 这条组合在本仓从未验证过，别用。
  （顺带：spec 下 `--deepep-mode` 要显式给 `normal`，`low_latency` 是给固定 batch 的
  decode 缓冲设计的，target_verify 的 token 数会变。）

### 4.3 TARGET_VERIFY 下 `seq_lens_cpu` 为 None（已修，插件侧）

```
File ".../sglang_kunlun/hooks/layers/attention/nsa/nsa_indexer.py", line 460, in _indexer_torch_ref
    assert forward_batch.seq_lens_cpu is not None
AssertionError
```

* 栈：`eagle_worker_v2.verify → run_eagle_verify → target forward → EB5DecoderLayer.forward
  → EB5AttentionMLA.forward_prepare → forward_absorb_prepare → indexer → forward_cuda
  → nsa_indexer._indexer_torch_ref`。
* **原因**：fork 只在普通 decode 的 batch 上填 `ForwardBatch.seq_lens_cpu`；
  TARGET_VERIFY / DRAFT_EXTEND_V2 的 batch 只有 device 侧（expanded）seq_lens。
  这个 assert 是"空 batch 快速返回"的前置守卫，语义上不需要 host 副本。
* **修法**（`code/sglang-kunlun/sglang_kunlun/hooks/layers/attention/nsa/nsa_indexer.py`）：
  空 batch 判定改用 device 侧 `forward_batch.seq_lens`，host 副本交给
  `_get_topk_paged` 内部的 `_seqlens_cpu(..., expanded=True)`（优先 metadata 的
  `*_cpu` 访问器，没有才回退一次 `.cpu()`）：

```python
    seq_lens_cpu = getattr(forward_batch, "seq_lens_cpu", None)
    if seq_lens_cpu is not None:
        is_empty_batch = len(seq_lens_cpu) == 0
    else:
        seq_lens_dev = getattr(forward_batch, "seq_lens", None)
        is_empty_batch = seq_lens_dev is None or seq_lens_dev.numel() == 0
    if is_empty_batch:
        return torch.full((x_meta.shape[0], self.index_topk), -1, ...)
```

* 修完就一路跑到 4/4 200，`_get_topk_paged` 在 verify 下**没有再报错**。

### 4.4 评估过、但本次**没有**触发的问题

* **`_topk_paged_torch` / `fast_topk_transform_fused` 的 expand 映射**（doc/5 P1、
  任务提示里的"`arange(rows) % req` 可能该用 `token_to_batch_idx`"）：
  `SGLANG_DSA_FUSE_TOPK` 默认 **True**，`metadata.topk_transform` 走的是 vendor 的
  `torch.ops.xspeedgate_ops.topk_transform(...)`，**显式带 `cu_seqlens_q`**，不经过
  那段 `_page_table_row_ids`；DSV4 的 EAGLE verify 在昆仑上已跑通过同一条路径
  （`3. eb5模型运行.md` §7.3），所以本次未改。**若以后把 FUSE_TOPK 关掉，这里要重新查。**
* **DeepEP 与 target_verify 的兼容性**：`deepep + normal` 下 verify 正常（这是
  `SGLANG_DEEPEP_NUM_MAX_DISPATCH_TOKENS_PER_RANK=256` 的配置），未观察到 dispatch 侧报错。

## 5. 接受率与加速比（实测）

测试口径：同一份 `tools`（见 §7），4 条不同 prompt 并发，`temperature=0`，
`context_length=8192`，`--disable-cuda-graph`，DP4/TP4/EP4，BF16。

| 配置 | 输出长度 | wall | 吞吐 | 相对基线 |
|---|---|---|---|---|
| 不开 MTP（基线） | 32 tok × 4 | 14.95 s | 8.56 tok/s | 1.00× |
| **MTP** | 32 tok × 4 | **11.44 s** | **11.19 tok/s** | **1.31×** |
| 不开 MTP（基线） | 96 tok × 4 | 44.34 s | 8.66 tok/s | 1.00× |
| **MTP** | 96 tok × 4 | **32.59 s** | **11.78 tok/s** | **1.36×** |
| 不开 MTP（基线，复跑） | 96 tok × 4 | 43.89 s | 8.75 tok/s | 1.00× |
| **MTP（复跑）** | 96 tok × 4 | **32.85 s** | **11.69 tok/s** | **1.34×** |

接受率（96 tok 那轮，`/metrics` 增量）：

```
spec_verify_calls_total      = 380      （384 个生成 token / 380 次 verify）
generation_tokens_total      = 384
spec_accept_length (gauge)   = 1.0      # 每步平均只出 1 个 token（bonus）
spec_accept_rate   (gauge)   = 0.0
```

* **接受长度 1.01**（≈1% 的步会多中一个 draft token），**接受率 ~0**。
* 这符合预期：8L 是**截断模型**，输出本身就是乱码；MTP 层是按 43 层的隐状态分布
  训练的，喂给它的 `hidden_states`（`hc_mult=4` 展平的 16384 维）已经不是训练分布，
  draft 的 top-1 基本不会命中 target 的 top-1。
* **所以 1.3× 不是 draft 命中的收益**：380 次 verify 只比 384 次 plain decode 少 4 步，
  但墙钟少了 26%（0.46 s/token → 0.34 s/token）。合理解释是 **target_verify 一次
  forward 吃 3 个 token，把"每步固定开销"（DP attention 的 metadata/all-gather、
  indexer 的 host 副本、逐层小 kernel 的 launch）摊薄了 3 倍**，而多出来的 draft
  forward 很便宜（1 层 + 5.3 GB 权重）。
  换句话说：**在"接受率≈0"的退化场景下仍然赚，是因为每步固定开销大；真模型上应该
  是"接受率收益 + 固定开销摊薄"叠加。**
* ⚠️ 这组数字**只说明链路与吞吐**，不能当成 MTP 的收益上限；要判断真实加速比，
  必须在不截断（整网 / INT8 整网）的权重上重测。

### 正确性：本模型上**无法**用输出比对来验证无损

投机解码在数学上应无损（greedy + verify 等价），但**这台机器上同一配置跑两遍输出就不一样**：

| 对比 | prompt0 | prompt1 | prompt2 | prompt3 |
|---|---|---|---|---|
| 基线 run1 vs run2（同参数） | 前 12 字符后分叉 | 前 3 | 前 0 | 前 49 |
| MTP run1 vs run2（同参数） | 前 159 | 前 3 | 前 0 | 前 49 |

即 **`temperature=0` 也不是逐字节确定的**（MoE dispatch/归约顺序、vendor kernel 的
atomics 都可能引入差异）。所以 MTP vs 基线的文本差异**既不能证明有 bug，也不能证明无损**。
要验证无损性需要先解决确定性推理（`--enable-deterministic-inference` 或固定 dispatch），
那是另一条线（可挂到 `4. 临时D2H与性能债.md`）。

## 6. 结论

1. **EB5 8L 的 MTP 能开、能跑**：draft 权重（`model.layers.43.*`，1583 张量）从整网
   checkpoint 取出来软链成独立目录即可，不需要重写权重、不需要改 target。
2. 链路上只有**两处**真问题，都在插件侧修掉：draft KV 池的 hook 挂错函数（§4.1）、
   verify 下 `seq_lens_cpu` 的硬 assert（§4.3）。
3. **不能用 `--moe-a2a-backend none`**（§4.2），EP>1 一律 `deepep` + `--deepep-mode normal`。
4. 接受率≈1.0（≈0%），因为 8L 是截断模型——**这是数据问题，不是实现问题**；
   端到端 1.31–1.36× 来自 verify 摊薄每步固定开销。
5. 下一步（按性价比）：
   * 在**整网 INT8（4 卡可跑，见 doc/6）**上开 MTP，拿真实接受率与加速比；
