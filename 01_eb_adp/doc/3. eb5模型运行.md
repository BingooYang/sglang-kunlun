> ## 🔴 最重要的一条：不要 `kill -9` 卡在 XPU 调用里的进程
>
> **这是本次踩得最惨的坑，请先读这一段。**
>
> 对"卡在 XPU 调用里"的进程（特征：CPU 100% 空转、GPU `0% util`、显存不涨）
> 执行 `kill -9`，会在设备上留下**杀不掉的 kernel** —— `xpu-smi` 显示
> `util = 100%`，但 `xpu-smi -q` 的 `Processes` 是 `None`。这种残留会**拖坏整个
> XPU runtime**：之后连 `torch.ones(1024, device='cuda')` + `sync` 都会间歇性挂死。
>
> 更糟的是驱动会**泄漏 "in use" 引用计数**：此后 `xpu-smi -r`（逐卡 HW reset，
> 官方唯一的用户态恢复手段）对**全部 8 张卡**都报
> `XPU ... is currently in use by another process`，**即使没有任何进程持有
> `/dev/xpu0..7` / `/dev/xpuctrl`**（逐 `/proc/*/fd` 扫过）。于是**只能节点级重启**。
>
> **正确做法**
>
> 1. 发现卡死**先等**（XPU 调用自带超时，给它时间自己出来），不要条件反射地杀；
> 2. 确实必须杀时，杀完要确认 **8 张卡都回到 `0 MiB / 0%`** 再起下一个任务
>    （`xpu-smi | grep 98304MiB`）；
> 3. 服务挂了**不要立刻重试**，先看 `xpu-smi` 是否全绿；
> 4. 脚本里那几行 `pkill -9` 清理逻辑**是有代价的**，只在确认没有 XPU 调用在飞时用。

### 7.2 两个真实阻塞点（都是干净异常，不是卡死）

**① `NotImplementedError: act_quant_kunlun unavailable on the fork`**

`EB5_KUNLUN_ADAPT_DIR`（本文要求 DSV4 也必须设，为了 `_init_raw` 那个 pad 绕行）会加载
`eb5_kunlun_adapt.py`，它注册了一个**假模块**
`sglang_kunlun.hooks.layers.attention.nsa.triton_kernel`，里面只有一个抛异常的
`act_quant_kunlun` 桩（原注释写"只有 `*_kunlun` 变体会用到"）。但 DSV4 的 indexer
量化路径**真的会调它**：

```
deepseek_v4 indexer.compute_q
 → kernel_ops.py fused_q_indexer_rope_hadamard_quant
 → dsv4_torch_shim.py:642 act_quant_kunlun(q_hada_2d, block_size=head_dim)
 → eb5_kunlun_adapt.py:281 → raise NotImplementedError
```

**修法**：把桩换成**能用的自包含实现**（与插件 `nsa/triton_kernel.act_quant_kunlun`
同实现，都是 `kunlun_ops.quant2d`）。改动落在
`01_eb_adp/test/eb5_kunlun_adapt.py` 与 `eb5_extra_adapt.py` 两处。

> ⚠️ **别图省事写成 `importlib.import_module("...nsa.triton_kernel")` 去复用真实现**。
> 那条 import 会拉起 `sglang_kunlun/hooks/layers/attention/__init__.py` 的 nsa redirect，
> **提前 import fork 的 attention 模块**，使适配层 `_TARGETS` 的补丁被**已经绑定的旧符号**
> 绕过。实测后果：`test_eb5_layer_modules.py` 从 **19 passed 退化成 4 failed**
> （`python/sglang/kernels/ops/attention/dsv4/dequant_k_cache.py:68
> TypeError: 'function' object is not subscriptable`）。

**② `RuntimeError: compressed_attention: win_kv_cache dtype must match q`**

`forward()` 无条件把 decode/extend 送进原生算子，但 DSV4 的 SWA KV cache 是
**uint8 字节缓冲**。fork 内存池注释把布局写得很清楚：

```
# BF16 layout: nope (448*2=896) + rope (64*2=128) = 1024 bytes/token
# FP8  layout: nope (448 fp8) + rope (64*2=128 bf16) + scales (7+1) = 584
```

实测 `kv_cache_total_dim = 584`（**FP8 布局**）。插件那段 uint8→bf16 重解释的条件是
`== 512 * 2`（1024，即 bf16 布局），FP8 布局**不命中** → uint8 cache 直接喂给算子 → 报错。

而插件自己的注释就写着 "The fp8 layout has no uniform view and is handled by the torch
paths instead" —— 只是 `forward()` 漏了这个分支。

**修法**：按插件自己的约定，FP8 布局（`swa_k_cache.dtype == torch.uint8`）改走
纯 torch 参考路径（`_dequant_sparse_keys` + `_sparse_mla_attention`）。
改动落在 `sglang_kunlun/hooks/layers/attention/deepseek_v4_backend.py`。

> 这个 dtype 问题**不是图捕获特有的**，关图模式下同样会撞到。之前关图没撞到，
> 只是因为更早的 `act_quant_kunlun` 先炸了 —— 修完①之后才暴露出来。

### 7.4 开图（`llgraph`）为什么还没通

FP8 布局现在走的是 torch 参考路径，而这条路径里有 **host 同步**
（`int(kvseqlen_cpu.max().item())`、index 操作），CUDA graph 捕获大概率不可用。

要真正开图，需要让原生 `compressed_attention` 能直接吃 FP8 布局 —— 那是**算子侧（KLX）**
的事；或者改 cache 的呈现方式（把 uint8 缓冲 `view` 成 q 的 dtype），但后者在混合布局下
**有静默算错的风险**，没有数值对齐手段时不要动。

### 7.5 停机：不要再手写 `pkill -9`

原来的两个 run 脚本里都有：

```bash
pkill -9 -f "sglang.launch_server" ; pkill -9 -f "sglang::"
```

**这段已经删掉**，换成 `01_eb_adp/tool/stop_kunlun.sh`。它有两个真实的坑：

1. **会打到调用者自己** —— `pkill -f` 匹配整条命令行，而调用它的命令本身往往就含这些
   字符串，于是把自己的 shell（甚至父 shell）一起杀掉，脚本半途而废。本次实测踩到两次
   （exit 137 / 143）。
2. **对 launcher 用 -9 会留 stuck kernel**（本文档开头那条）。

`stop_kunlun.sh` 的分级策略：

1. 先给 launcher 发 **TERM+INT**（sglang 有优雅退出 handler）；
2. launcher 主线程通常卡在 `waitpid` 等子进程，而 `sglang::tokenizer_worker` /
   `detokenizer` **不响应 TERM/INT**，handler 永远走不完 —— 这就是"发了信号也退不掉"的真因；
3. 于是**只对这两类空闲的纯 CPU worker 用 -9**，解开 `waitpid` 死锁。
   判据：角色上它们只做分词/反分词、不发任何 XPU 调用；实测状态为 `S` +
   `ep_poll`/`futex_wait`，且 `xpu-smi -q` 不登记它们。状态不像空闲 worker 就**跳过不杀**；
4. **launcher 本身一次 -9 都不发** —— 子进程被回收后它会在几秒内自己走完 handler
   （实测 **5 秒**）；
5. 最后校验 8 张卡都回到 `0 MiB / 0%`，不满足就报错退出，交给人看。

两个 run 脚本现在都通过它做启动前清理，清不干净就直接放弃启动（不硬上）。

### 8.2 第 1 次起服务：首次前向的设备级 kernel 异常

模型 6144 个分片加载完（约 2.5 分钟），**首次前向**即崩：

```
ernie5.py:3644  forward → self._mhc_pre(...)
ernie5.py:3587  _mhc_pre → _mhc_pre(...)
sglang/kernels/ops/layernorm/mhc.py:1176  mhc_pre → kernel_0(...)
sglang-kunlun/01_eb_adp/test/eb5_kunlun_adapt.py:124  kernel_0
    sqrsum_partial[s, :n].copy_((xs * xs).sum(-1))
torch.AcceleratorError: CUDA error: wait for noc idle timeout
kl3ChannelCheckErrors ... status= 299
```

8 个 rank 全崩，scheduler 全部 `exit code -3`。dmesg 里紧跟 **4 个设备**的
`KL_XID_KERNEL_EXCEPTION`（`ch=3`，22:34:18–22:34:31）。

> **注意 traceback 的自我声明**：`CUDA kernel errors might be asynchronously reported
> at some other API call, so the stacktrace below might be incorrect` —— 所以
> `eb5_kunlun_adapt.py:124` 未必是真凶，得用 `CUDA_LAUNCH_BLOCKING=1` 才准。
> 但它把范围缩到了 `mhc_pre` 的 splitk 拆解（`kernel_0`）这一块，
> 与第六节待办里写的"EB5 的 `mhc_pre` splitk 拆解"一致。

形状契约本身是对的（对着 `mhc.py:1120-1180` 核过）：

```
hc_hidden_size=16384, split_k=n_splits_pre=16 → split_size=1024
partial_out   = (16, num_tokens, 32)   → out_partial[s, :n, :j]      (j = min(hc_mult3, ...))
partial_sqrsum= (16, num_tokens)       → sqrsum_partial[s, :n]
xs = xf[:, lo:hi]  → (n, 1024)
```

即切片/矩阵乘的维度都能对上，**不是简单的 shape 越界**，更像设备级 kernel 异常。

### 8.3 第 2 次起服务：退化成 XCCL/D2H 挂死

带 `CUDA_LAUNCH_BLOCKING=1` 重跑（为了定位真凶），结果**在加载权重刚开始就挂死**，
连 XCCL 初始化日志都没有（`XCCL version` 计数 = 0）：

```
[22:38:20 DP4 TP4 EP4] Load weight begin. avail mem=95.75 GB
[22:38:20 DP4 TP4 EP4] EB5 MLA+HCA plan: 44 entries, ...   ← 日志到此为止
```

现场：

| 项 | 值 |
|---|---|
| `sglang::scheduler_DP0/DP1/DP2` | 状态 `R`，CPU **~94% 空转**，持续 12 分钟 |
| 对应 3 张卡 | **util 100%**（另 5 张 0%） |
| 日志 | 20 s 内 **0 字节**增长 |
| `xpu-smi -q` | 登记 **8 个**进程 |

这与第四节的「最小复现」**同型**：`init_process_group(nccl, ws=8)` 场景下
**rank 0/1/2 挂死**。也就是说 8.2 那次 kernel 异常之后，设备就退化了 ——
**"kernel 异常 → 设备退化 → rank 0/1/2 挂死"这条链完整重演**。

### 8.4 本次的处置（安全第一）

- 挂死后**只等不杀**：连续观察 12 分钟（`R` + 94% CPU + 100% util + 日志零增长），确认是永久挂死而非慢
- **全程没有对 launcher / scheduler 用 `-9`**（它们正卡在 XPU 调用里，正是本文开头禁止的动作）
- 第 1 次崩溃后的残留是用 `tool/stop_kunlun.sh` 清的（它只对**空闲的纯 CPU worker** 用 -9，launcher 一次都没挨 -9）
- **未尝试 `xpu-smi -r`**（第五节说它被泄漏的 "in use" 引用计数挡住；且它是逐卡 HW reset，需要人工确认后再动）

### 8.5 结论与下一步

1. **EB5 起不来的根因是 8.2 那个设备级 kernel 异常**，触发点在 `mhc_pre` 的 splitk 拆解
   （`eb5_kunlun_adapt.py:99-127` 的 `kernel_0`）。这是**先于**一切配置问题的硬阻塞 ——
   它就是第六节待办的第一条，本次独立复现确认。
2. 修它的顺序建议：先用 `CUDA_LAUNCH_BLOCKING=1` **在一张卡上**把真凶缩到一个具体的
   `aten` op（本次因为设备已退化，没走到这一步就被 XCCL 挂死挡在前面了），
   再决定是改 `kernel_0` 的写法还是交给 KLX。
3. **设备恢复**：本次是"kernel 异常 + rank 0/1/2 挂死"的组合，按第五节需要**节点级恢复**。
   恢复后再按 7.1 跑一次 XCCL 探针确认 8/8，再谈 EB5。

## 九、更正与补充：设备存在"半坏"状态（2026-10-17 深夜）

第八节有两处结论被后续实测推翻，这里更正。

### 9.1 更正一：挂死**不是永久的**，约 20 分钟后会自行超时退出

第八节 8.3 记的那次挂死（22:38:20 起），到 **22:58:24** 自行收尾：

```
RuntimeError: Rank 0 scheduler died during initialization (exit code: -3)
```

即挂了约 **20 分钟**后，XPU 调用自带的超时兜底生效，进程正常退出、显存释放。
所以 8.3 说的"永久挂死"应更正为"**会长时间挂死（十几到二十分钟），但最终能自己退**"。

> **推论：挂死时更不能 kill。** 你等它 20 分钟，它会干净地退；你 `kill -9`，
> 就变成本文开头那种"引用计数泄漏、只能节点级重启"的局面。

### 9.2 更正二：设备会进入"**通信能通、算力不能用**"的半坏状态

第八节之后，设备已经显示 8 卡 `0MiB / 0%`、8 进程 XCCL 探针 **8/8 通过**。
然后**在单卡上**跑 EB5 单测，`test_mhc_pre_big_fuse_with_norm_tilelang_kernel` 直接挂死：

```
assertTrue (unittest/case.py:685)
test_mhc_pre_big_fuse_with_norm_tilelang_kernel (test_eb5_hc_pre.py:154)
    self.assertTrue(torch.isfinite(post_mix).all())
```

（栈是用 `py-spy dump --pid <pid>` 读的 —— 只读、不发信号，挂死时的首选诊断手段。）

现象：单卡 util **100%**、进程 CPU **101%** 空转十几分钟，**且不产生新的 Xid**。

**这条推翻了一个很自然的假设**：`xpu-smi` 全绿 + XCCL 探针 8/8 **≠** 设备健康。
判据必须再加一个**真实算力探针**（已实现为 `tool/compute_probe.py`：小 GEMM +
逐行平方和 + `isfinite().all()` 同步 —— 正是这次挂死那条路径的同型算子）。

> 同时也说明第五节"需要节点级恢复"的结论**依然成立**：半坏状态靠等、靠探针都回不来，
> 得重载驱动。

### 9.3 恢复判据（更新版）

起服务前必须**四项全过**（`tool/preflight.sh` 已实现，任一不过就拒绝启动）：

| # | 检查 | 判据 |
|---|---|---|
| 1 | 设备空闲 | 8 张卡都 `0MiB / 0%` |
| 2 | 设备未受新伤 | dmesg 的 `KL_XID_KERNEL_EXCEPTION` 计数不比基线高 |
| 3 | 通信可用 | 8 进程 XCCL 探针 **8/8** |
| 4 | **算力可用** | 8 张卡各跑一次真实算力探针 **8/8** |

第 3、4 项**不可互相替代** —— 9.2 就是"3 过、4 挂"的实例。

### 9.4 顺带：`timeout` 也不是护栏

单测那次挂了 19 分钟，而外面包的 `timeout 600` 早在第 10 分钟就发了 SIGTERM ——
**完全无效**（进程卡在 C 调用里，信号处理器跑不到）。所以：

- 别把 `timeout` 当护栏，它只会让你误以为"已经杀掉了"；
- **更不要用 `timeout -k`** —— 那会在超时后升级成 SIGKILL，正好踩中本文开头那条。

### 10.1 硬约束：4 卡装不下完整模型

### 10.3 根因：适配层引入了原始 kernel 没有的 **D2H 同步**

`dp_attention.memcpy()` 传入的 `offset` / `sz` 是 **0-dim CUDA tensor**
（`get_dp_local_info()` 返回 `global_num_tokens_gpu` 的切片）。原始 triton kernel
把它们当 **device 指针**，在 kernel 内 `tl.load`，**全程没有 D2H**：

```python
# kernels/ops/memory/memcpy_triton.py（原始）
offset = tl.load(offset_ptr).to(tl.int64) * chunk_size
sz     = tl.load(sz_ptr).to(tl.int64)   * chunk_size
```

适配层写成 `int(offset)` → 标量 D2H → 本机 XPU 上把所有 rank 一起挂死。

**修法（已落地）**

1. `eb5_extra_adapt.py::memcpy_triton`
   改成纯 device 侧：`arange` + 布尔 mask 完成动态切片。
   CPU 上与原始语义 **342/342 组输入逐元素一致**（偏移 / 截断 / 双向 / 不同尾维）。
2. `eb5_extra_adapt.py::fused_split_feature_topk`
   `int(num_token_non_padded)` 同为 device 标量 → 改 `torch.where(rows >= lim, ...)`，
   5 种截断值语义一致。

> **这类缺陷的排查口径**：看到适配层的 `int(x)` / `.item()` / `.cpu()` / `.tolist()`，
> 先确认 `x` 是否 device tensor。整份适配层已逐个核对调用点，其余
> （`extend_seq_lens_sum` / `num_tokens` / `num_seq` 等）都是 Python int，不会同步。

### 10.4 脚本改造

   - `PREFLIGHT_GPUS=4,5,6,7`：只检查/探测这些卡，N 进程 XCCL + N 卡算力探针；

### 11.2 8 层子模型：构建命令与硬约束

### 11.3 设备闸门 preflight


可调项：`PREFLIGHT_GPUS`（卡子集）、`PROBE_PORT`（XCCL 集合通信端口）、

> ⚠️ `preflight.sh` 超时**不会**回收探针进程 —— 它明令"不要 kill"。
> 探针会自己挂十几到二十分钟（§9.1），**这期间 8 张卡都被 `166MiB` 占着**，
> 不能起下一轮 preflight，也不能起服务。

**卡坏了怎么修（2026-10-20 新结论，修正 §5 的"只能节点级重启"）**：处于"任何 device op 都挂"
状态的卡，用**每卡强制复位**就能救回来：

```bash
timeout 180 xpu-smi -fr -i 4,5,6,7     # -fr = --force-xpu-reset；-r 报 "in use" 时用它
# 期望 4 行 "XPU 00000000:xx:00.0 was successfully reset." + "All done."
```

### 11.7 必知坑（本次又踩到的，全部有实测支撑）

1. **KV cache 必须显式 bfloat16**（`run_eb5_kunlun.sh` 已默认）。
   `--kv-cache-dtype auto` 会落到 FP8(uint8) 布局，SWA 的 K 写入走
   `dsv4_torch_shim._e4m3_to_uint8` 里的 `.cpu()` → 4 rank 首次前向永久停在那个 D2H。
2. **挂死一律不要 kill**（§开头 + §9.1）。判据是"日志零增长 + 多个 scheduler 栈相同"，
   取证用 `py-spy dump --pid <pid>`（只读）或 `tool/diag_hang.sh`。退出方式是等：
   - 服务：scheduler watchdog **300 s** → `exit code -3`（本次 19:12:3x 挂、**19:19:40** 退出）；
   - 探针：XPU 调用自带超时，**15–20 min**（本次 8 卡探针 18:57 起、**19:14–19:15** 退）。
3. **每次"挂死 + 自行退出"都会留 4 条 `KL_XID_KERNEL_EXCEPTION`**（`ch` 表示是哪种收尾：
   `ch=2` = scheduler 退出、`ch=1`/`ch=0` = 探针退出）。本次一轮里 20 → 24 → 28 → 32，
   四次各 4 条，**没有一次是 kill 出来的**。所以"Xid 未增"只能当"这一轮有没有新伤"的指标，
   不能当"设备是好的"的证明。
4. **半坏的判据是"任何 device op 都挂"，不是显存/util**：卡 `0MiB/0%`、`Processes: None`，
   但 `torch.tensor([1.0], device="cuda")`（`xccl_probe.py:28`）就永久停住；
   夹在中间的形态是 XCCL N/N 过、算力 0/N（§9.2）。
5. **`timeout` 不是护栏**（§9.4）：进程卡在 C 调用里，SIGTERM 跑不到 handler；
   `timeout -k` 会在超时后升级 SIGKILL，正好踩中第 2 条。
6. **换组卡要换 `PROBE_PORT`**：上一轮挂住的探针还占着 `29511`，新探针会直接连上旧 group。
7. **上一轮还有进程占卡时先等**（`xpu-smi` 的 `Processes` 表 + `ps`）。本次 19:11 有一次
   **并发会话**起的 8L 服务占了 0–3，只能等它 watchdog 退出后再用 `stop_kunlun.sh` 收尾
   （launcher 收到 TERM 后 5 s 内自己退，未用 `-9`）。
8. **单测有个过期阈值**：`test_eb5_adapt_coverage.py:60` 断言"被替换符号 ≥ 25"，
   融合实现删除后实际是 **24** → 该用例恒 fail（语义用例
   `test_every_replaced_symbol_is_referenced_by_some_test` 仍通过）。属测试债，不是功能缺陷。
9. **`port_base ... is not available in 30 seconds`**：上一轮 launcher 没退干净（scheduler 崩了
   但 launcher/worker 还在）时，新服务会在 `wait_port_available(port_base)` 上耗 30 s 然后
   `ValueError` 退出，表现是"HTTP 起来了但永远 503"。**先 `bash tool/stop_kunlun.sh` 再起**。
10. **`AttributeError: 'EB5FullMLAIndexer' object has no attribute 'nsa_enable_prefill_cp'`**
   （`sglang_kunlun/hooks/layers/attention/nsa/nsa_indexer.py:783`，20:12 实测）：
   DSV4 的 indexer 叫 `nsa_enable_prefill_cp`，EB5 的叫 `dsa_enable_prefill_cp`。
   插件里已有 `_enable_prefill_cp(module)` helper，两处调用点必须走它（或
   `getattr(self, "dsa_enable_prefill_cp", False)`），否则**每个 extend 前向都抛异常**。
11. **`repro_multirank.sh` 的空闲卡检查有同一个 pipefail bug**（11.3 的 `preflight.sh` 已修，
    这个脚本没修）：`xpu-smi -i "$d" | grep -q …` 在 `set -o pipefail` 下会因 SIGPIPE(141)
    判失败，**空闲卡被误判成占用**（本次实测 4-7 明明 `0MiB` 却报 `0/4` / `3/4`）。
    修法同 preflight：先 `out=$(xpu-smi -i "$d" 2>/dev/null) || continue`，再 `grep -qE … <<<"$out"`。
    绕过办法：直接跑 `repro_multirank.py`（`RANK` / `WORLD_SIZE` / `REPRO_DEVICE` / `MASTER_PORT`）。
12. **同一节点上并发跑多个服务会互踩**：`run_eb5_kunlun.sh` 里 `--nccl-port 9999` 是写死的，
    两个服务同时起会抢同一个 XCCL 引导端口；另外每个 launcher 在**全部可见卡**上留 ~32MiB
    上下文，会把别人的"空闲卡"闸门判成占用。起服务前用
    `ps -eo args | grep sglang`、`ss -ltn | grep -E ':9999|:30087'` 各看一眼。

### 11.10 结论与下一步

1. **本次的硬阻塞是设备，不是代码**：两组卡（0–3、4–7）XCCL 探针都 0/N，
   连 `torch.tensor(..., device="cuda")` 都挂 —— 与 `problem/2026-10-20-mhc-hang.md` §3
   的"任何 D2H 都挂"完全同型。适配层这轮**没有**新增改动。
2. **恢复只有一个办法**：节点级重启（§5）。重启后按 11.3 → 11.4 → 11.5 → 11.6 顺序走，
   每级不过就停，别跳级。
3. 重启后的**第一目标**不是整网，而是第 2 级的 `mhc-pre` / `mhc-post` 两个 case：
   19:11 那次唯一的栈指向 `mhc_pre_torch_ref` 的 sinkhorn 段（3 token 的小形状），
   需要在健康设备上先确认"散算子路径在 4 rank + 3 token warmup 下不挂"。
4. 如果健康设备上第 3 级仍挂在第 5 段（`pre_mhc(ffn)`），排查顺序：
   ① （已过时，见上）`EB5_MHC_TORCH_REF` / `EB5_MHC_SINGLE_SPLIT` 均已删除；mHC 的 `mhc_pre` / `mhc_post` 由适配层在 **kernel 级**换成 torch；
   ② 用 `CUDA_LAUNCH_BLOCKING=1` 在单卡上把真凶缩到一个 `aten` op；
   ③ 对照 DSV4 的 `hc_pre_torch_impl` / `hc_split_sinkhorn` 逐式核对（§4.1 已做过一轮）。
5. 顺手要清的两笔债：`test_eb5_adapt_coverage.py:60` 的阈值（25 → 24）；
   `mhc_post` 之后可换成 `kunlun_ops.hc_post_kunlun_impl` 做性能对照（§4.2）。

## 十二、通用规则：昆仑上不要用 Triton，算子一律 torch 化（2026-10-20）

> 这是**跨模型、跨算子**的通用规则：EB5 / DSV4 / 以后新接的模型都适用。

### 12.1 规则

**昆仑 P800 没有 Triton 后端。所有 `@triton.jit` 算子、以及 `kernel[grid](...)` 形式的调用，
一律改成纯 torch 散算子**（必要时用 `kunlun_ops` / `xspeedgate_ops` 的原生算子）。
不要试图打桩、包一层 `__getitem__`、或想办法让 Triton 编过去 —— 那只是把错误推迟到运行期，
而且会在"看起来已经跑通"的路径上留下隐患。

### 12.2 为什么（实测依据）

- 运行时启动即告警：`fla/utils.py: Triton is not supported on current platform, roll back to CPU`
- fork 里的 triton 调用形如 `kernel[grid](...)`。插件把 kernel 换成普通 Python 函数后，
  直接 `TypeError: 'function' object is not subscriptable`
  （2026-10-20 的 `transform_index_page_table_prefill_kernel` 就是这一类）
- `sgl_kernel.fast_topk_transform_fused` 在昆仑侧是**未实现的 stub**，调用即炸
  （`metadata.topk_transform` 的 skip_logits 分支）

### 12.3 怎么改

1. **逐行对照原 kernel**：输入/输出 shape、dtype、越界与空洞的填充值、累加顺序
2. 用 `gather` / `scatter` / `arange` / `where` / `einsum` / `matmul` 表达；
   **禁止 Python 逐元素循环**（会把几十 ms 的 kernel 变成几十秒）
3. 保持函数签名与返回结构不变，**不要改调用方**

   按 token 分块，或 bf16 输入 + fp32 累加

### 12.6 通用原则：Triton / tilelang / deep_gemm 一视同仁（2026-10-20 补）

昆仑 P800 **没有 Triton**（`triton.jit` 被 stub），也**没有 tilelang / deep_gemm**。
因此对这三类 kernel 只有一条路：

> **在 kernel 级（或直接调用点）改成纯 torch 散算子**，用
> `gather / scatter / index_select / arange / where / cumsum / searchsorted`
> 表达；确实需要原生算子时用 `kunlun_ops` / `xspeedgate_ops`。
> **不要**给 `@triton.jit` 打桩、也不要包一层 `KernelLauncher` 让
> `kernel[grid]` 能下标——那只是把错误推迟到下一次调用。
> 保持原函数签名、返回结构、dtype、填充值（越界/空洞填 `-1`）与数值语义不变。

已按此原则处理的清单（EB5 8L 链路）：

| 文件 | 原实现 | 现实现 | 验证 |
|---|---|---|---|
| `kernels/ops/attention/dsa/transform_index.py` | `transform_index_page_table_prefill_kernel[grid]` | `searchsorted` + 行 `index_select` + `gather` + `where` | 与同文件 `_prefill_ref` **逐元素相等**（8 组：extend 长度 1/3/4、expanded on/off、含 padding 行） |
| 同上 | `transform_index_page_table_decode_kernel[grid]` | 行对齐 `gather` + `where` | 与 `_decode_ref` 相等 |
| 同上 | `prepare_trtllm_nope_sparse_metadata_kernel[grid]` | `(page_table >= 0).sum(1)`，空行填 dummy 0 | 逻辑对照 |
| `internal/layers/attention/mla_hca/dsa_swa_index.py` | `_append_indexer_swa_kernel[grid]` | `arange` 掩码 + 前缀/尾部 gather + flat-index `index_select` + `scatter_` | 与 Python 逐元素参考相等（RAGGED / PAGED_IDENTITY / PAGED_MAPPED 三种 mode，含 2048+128 大 shape） |
| `srt/mem_cache/allocator/paged.py` | `alloc_decode_kernel[grid]` | `cumsum` 前缀 + `index_select` + `where`（分支用 host 端 `free_pages.numel()`，避免 D2H） | 语义逐行对照 kernel |
| `01_eb_adp/test/eb5_mla_adapt.py` | `kvs = kv.float()`（整块 KV 升 fp32） | 先 gather 出 `[s_q, topk, d]` 再 `.float()` | 修 42.51 GiB OOM |
| `01_eb_adp/test/eb5_*_adapt.py` | `mhc_pre` / `mhc_post` 融合（tilelang/deepgemm） | kernel 级 `mhc_pre_torch_ref` / `mhc_post_torch_ref`（另一 agent） | 128 组 CPU 对照 bit-identical |

踩坑记录（都是同一类）：

1. `triton` 被 stub 成普通函数后，`kernel[grid]` 报
   `TypeError: 'function' object is not subscriptable`；`@triton.jit` 的函数
   一旦被调用还会报别的怪错。**看到 `[grid]` 就要改，不要等它报错**。
2. 纯 torch 改写要避免 `.item()` / `bool(tensor.any())` 这类 **D2H 同步**：
   昆仑设备半坏时它们会永久挂住。分支条件尽量用 host 已知量
   （`tensor.numel()`、`sum(extend_lens_cpu)`）。
3. 逐元素改写必须核对**填充值**与**行/列语义**：prefill 的 topk 是"行内位置"，
   要经 `page_table_1` 映射成 slot；decode 是"行对齐"；window 段的 RAGGED 用
   `ragged_offsets + position`，PAGED 用 `page_table[row, pos//page_size]*page_size + pos%page_size`。
4. `clamp_` 是**就地**操作：`swa_len = seq_len.clamp_(max=window)` 会顺手改掉
   `seq_len`，后面的 `position = seq_len - swa_len + w` 全错（已踩，改为 out-of-place）。

### 11.13.2 首包 rank skew：晚绑定 kernel 的修复 pass 落在 forward 里

现象（修复前，4 个 rank 的 `eb5-mhc-trace` 计数）：

```
[r0] 2160   [r1] 2160   [r2] 2160   [r3] 1487      # 全部停在 pre:norm，无异常、无新 Xid
```

`py-spy` 显示 DP3 的 scheduler 正在跑
`kernel_ops: repair pass start, tracking 64 originals` —— 也就是
`nsa_indexer.py::_fix_late_kernel_bindings()`。它要 `import` 一批**晚加载模块**
（`mem_cache.allocator.paged` / `attention.dsa.transform_index` …）再全量重扫
`sys.modules`（8000+ 模块），**每个进程只做一次，但做的时刻取决于第一次 indexer 调用**。
DP0–2 在加载期就做完了，DP3 拖到首个 forward 里做，于是 4 个 rank 在 DP all-gather 上
互相等，看起来像挂死。

修复：在 `ModelRunner.load_model` 的 AFTER hook
（`sglang_kunlun/hooks/model_executor/model_runner.py::_repair_kernel_bindings`）里，
权重加载完成后立刻调用一次 `_fix_late_kernel_bindings()`，让 4 个 rank 在 **ready 之前**
完成同一遍修复。修复后同一配置下 trace 变成 **2160/2160/2160/2160**，并且立刻暴露出
真正的问题（卡点 4 的 `fast_topk_transform_fused`），不再表现为"静默挂死"。

* 起服务：port `30082`、`CONTEXT_LENGTH=32768`、`--dsa-topk-backend torch`。
  **没能走到 ready**，三次尝试的原因分别是：

| 尝试 | 日志 | 结果 |
|---|---|---|
| 1 | `logs/eb5_kunlun_20261020_225426.log` | `MEM_FRACTION=0.90` → `Memory pool end avail mem=11.84 GB` 之后，首个 forward 在 `_store_bf16_rows`（`fused_k_norm_rope_flashmla_bf16`）申请 **38 MB** 临时缓冲 → **OOM**（`90.19 GiB allocated / 96 GiB`） |
| 2 | `logs/eb5_kunlun_20261020_225912.log` | 改 `MEM_FRACTION=0.85` → pool 正常（`avail mem=14.83 GB`，`max_total_num_tokens=107008`），加载到 91 GB/卡时被**并发会话的 `stop_kunlun.sh`** TERM 掉 |
| 3–5 | `…_230853/231334/231848.log` | 同上：都在加载/建 pool 阶段被并发会话收走；期间本机同时出现两个 8 卡整网 launcher（互相抢 534 GB 权重），必然 OOM |

**整网 OOM 的结论（可直接抄）**：43 层整网在 8 卡上必须 `MEM_FRACTION<=0.85`。
`0.90` 时 KV pool 会把卡吃到只剩 28 MB，`_store_bf16_rows` 那 38 MB 的临时缓冲就炸。
`run_eb5_kunlun.sh` 的默认值已改成 `0.85`（带注释）。

**整网仍未 verified**（没拿到过 200 + 非空文本），下一步就是：单进程、独占 8 卡、
`MEM_FRACTION=0.85`、`--dsa-topk-backend torch`，再跑 11.13.3 的 4 并发判据。

> 注：整网与 8L 抢同一批卡。本轮多次出现**并发会话的 `stop_kunlun.sh` 把在跑的服务
> SIGTERM 拆掉**（日志里是 `Stopping parent process [...]` / `kill_process_tree`），
> 8L 前后被打断 3 次。**同一台机器上不要同时跑两条 8L/整网流水线**：`stop_kunlun.sh`
> 是按进程名全局清理的，会把别人的服务一起收掉。
