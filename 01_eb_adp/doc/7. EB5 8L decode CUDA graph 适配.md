> 建立于 2026-10-21。目标：把 EB5 **8 层 BF16** 子模型的 decode 阶段从 eager 切到

## 3. 尝试过的开关组合与结果

| # | 关键开关 | 结果 | 证据 |
|---|---|---|---|
| A0 | `--disable-cuda-graph`（基线）+ `--deepep-mode normal` | ✅ 4/4 200，稳定 | `logs/eb5_kunlun_20261021_114816.log` |
| A1 | `--cuda-graph-config {"decode":{"backend":"full","max_bs":8,"bs":[1,2,4,8]}}` + `--deepep-mode normal` | ❌ **图被框架强制关掉**，服务仍是 eager | `logs/eb5_kunlun_20261021_115155.log:189` |
| A2 | 同上，但 `--deepep-mode low_latency`（默认）+ `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` | ❌ 捕获进入模型前向，**挂死**（>4 min 不结束） | `logs/eb5_kunlun_20261021_115608.log` |
| A3 | A2 + 去掉 `expandable_segments`（`PYTORCH_CUDA_ALLOC_CONF` 不设） | ❌ 同样挂死 | `logs/p17_20261021_120344_p30110.log` |
| A4 | A3 + `--json-model-override-args {"hc_sinkhorn_iters":1}`（把 sinkhorn 迭代从 20 降到 1） | ❌ 仍挂死，只是**卡在更靠后的 op** | `logs/p17_20261021_120826_p30110.log` |
| A5 | A4 + `--moe-a2a-backend none`（绕过 DeepEP） | ❌ 仍挂死，卡在另一个 op | `logs/p17_20261021_121205_p30110.log` |

**结论 1（框架约束）**：`--deepep-mode normal` 会**无条件**把 decode/prefill 两个 phase 的 graph
都设成 `disabled`，即使命令行显式给了 JSON 配置：

```python
# code/sglang/python/sglang/srt/arg_groups/moe_hook.py:308
if a2a_backend == "deepep":
    ...
    if cfg.deepep_mode == "normal":
        logger.warning("Cuda graph is disabled because deepep_mode=`normal`")
        declare_resolution(server_args, "_handle_a2a_moe",
                           cuda_graph_config=with_phase(cfg.cuda_graph_config,
                                                        Phase.DECODE, backend=Backend.DISABLED))
        declare_resolution(server_args, "_handle_a2a_moe",
                           cuda_graph_config=with_phase(cfg.cuda_graph_config,
                                                        Phase.PREFILL, backend=Backend.DISABLED))
```

服务启动日志里能直接看到这条（`eb5_kunlun_20261021_115155.log:189`），随后 `server_args` dump 里
`cuda_graph_config.decode.backend = 'disabled'`（但 `max_bs` / `bs` 保留，说明 JSON 被解析了、只是
被 `moe_hook` 覆盖）。**所以：想要 decode graph，必须 `--deepep-mode low_latency`。**

**结论 2（捕获参数）**：`max_running_requests=4 / dp=4` 下每 rank 只有 1 条在跑，实际捕获桶就是
`bs=[1]`（日志：`Capture target decode CUDA graph begin. backend=full, num_tokens_per_req=1, bs=[1]`），
显式给 `bs=[1,2,4,8]` 不会多捕桶。要做多桶，得把 `--max-running-requests` 提到 `dp_size × N`。

## 4. 失败点逐条

### F1（已定位，框架行为，非 bug）`deepep_mode=normal` 强制关图

- **现象**：给了 `--cuda-graph-config {"decode":{"backend":"full"}}`，启动后 `cuda_graph={decode=0.00}`。
- **位置**：`sglang/srt/arg_groups/moe_hook.py:308-323`。
- **原因**：DeepEP normal 模式（prefill 用）没有 graph 化的 dispatch 实现，框架直接关两个 phase。
- **是否已修**：不需要修，绕开即可（改 `low_latency`）。
- **影响**：这是「必须 low_latency」的硬前提，而 low_latency 又引出 F3/F4。

### F2（已定位，插件侧风险）low_latency 的 masked MoE dequant 一次非法访存

- **现象**（2026-10-21 11:15，第一次 low_latency + eager 试跑，**与开图无关**）：
  服务 ready 后第一个 warmup 前向，DP3 抛
  ```
  File ".../ep_moe/layer.py", line 1260, in forward_deepgemm_masked_bfp16
      per_token_dequant2d_with_mask(...)
  File ".../kunlun_ops/_xflashinfer_quant.py", line 320
      ret = xpu_flash_ops.dequant2d_per_token(x, scale, y, recv_count, is_absmax, force_sdnn)
  RuntimeError: optimized_ops::dequant2d_per_token failed r=2
  ```
  随后 `CUDA error: an illegal memory access was encountered`，dmesg 记 `KL_XID_KERNEL_EXCEPTION`（dev0）。
- **原因**：`hidden_states` 是 DeepEP LL 量化下发的 **int8**，走 `is_absmax=True` 反量化；该 kernel 在实际
  服务形态下失败（当时设备刚经历过一次崩机，不能排除设备半坏放大）。
- **独立验证**：`.build/p17_dequant_probe.py` 用**真实形态**（`G=128, M=256, N=2048`，int8 x、
  fp32 scale `[G,M,1]`、int32 `recv_count`、bf16 y）单独跑，**4 组全部通过且数值与参考一致**
  （`RESULT: ALL_OK`）。说明 kernel 本身可用，服务里的失败更像**设备状态**或**上游 buffer/stride** 问题。
- **是否已修**：未修（未复现于干净设备上的后续 low_latency 起服务；A2–A5 都过了这一步）。
  后续要复现，建议在 `forward_deepgemm_masked_bfp16` 里加 `EB5_MOE_TRACE=1` 打点（打印
  `hidden_states.shape/stride/masked_m.dtype/recv_count.max()`）后再判。

### F3（**核心阻塞**）整图捕获挂死在模型前向里

- **现象**：`Capture target decode CUDA graph begin. backend=full, num_tokens_per_req=1, bs=[1],
  avail mem=31.84/33.42 GB` 之后**再无输出**，4 个 rank 全部 100% util（显存 ~70.5 GB / 96 GB），
  CPU 每 rank ~100%（累计 CPU 时间持续增长），4 分钟以上不推进。
- **栈（py-spy，三次不同配置分别命中三个不同 op）**：

  A2/A3（20 次 sinkhorn 迭代）：
  ```
  _hc_split_sinkhorn_torch (01_eb_adp/test/eb5_kunlun_adapt.py:599)   # comb / (comb.sum(dim=1)+eps)
  mhc_pre_torch_ref (eb5_kunlun_adapt.py:687)
  _mhc_pre (internal/models/eb5/ernie5.py:3635)
  forward (ernie5.py:3737)
  run_once (runner/decode_cuda_graph_runner.py:1189)
  capture_one (runner_backend/full_cuda_graph_backend.py:144)
  ```

  A4（`hc_sinkhorn_iters=1`，绕过 sinkhorn 后往下走了一层）：
  ```
  _gather_bytes (01_eb_adp/test/eb5_mla_adapt.py:838)
  _mla_gather_kv (eb5_mla_adapt.py:921)
  flash_mla_with_kvcache (eb5_mla_adapt.py:964)
  forward (hooks/layers/attention/deepseek_v4_backend.py:2275)
  _forward_hca (backend.py:369)
  ```

  A5（`--moe-a2a-backend none`，绕过 DeepEP）：
  ```
  rmsnorm (kunlun_ops/_xflashinfer_norm.py:488)
  rmsnorm (sglang_kunlun/kernels/sgl_kernel_kunlun/layernorm.py:35)
  _compress_norm_rope_store_kunlun (sglang_kunlun/kernels/dsv4_torch_shim.py:1158)
  compress_norm_rope_store_bf16 (kernel_ops.py:2643)
  _forward_compress_all_in_one (dsv4/compressor_v2.py:216)
  ```

- **原生栈（关键）**：CPU 不是在等锁，而是在 **driver 的 kernel 下发里自旋**：
  ```
  sched_yield (libc)
  libxpucuda.so ... -> xpu_launch_async (libxpurt.so)
  xpukernel_xpu3::tensor_calc_scalar / xdnn_pytorch::add_scalar / add_tensor
  _hc_split_sinkhorn_torch (eb5_kunlun_adapt.py:599)
  ```
  即 **launch queue 满了**，说明卡上有一个 kernel 一直不结束（设备 100% util），CPU 只是被反压住。
- **不是设备故障**：这几次挂死期间 `dmesg` 在 **dev0–3 上没有新的 KL_XID**（同期 dev4 的 Xid 属于
  4–7 上的另一个任务），进程退出后显存自动回到 0 MiB。
- **不是单个 op 的问题**（见 §5）：同一批 op 单独 capture+replay 全部通过。
- **推断**：挂死与「**整图（≈ 数千个节点）+ 4 rank 同步**」有关，而不是某个算子。最可能的两类原因：
  1. **DeepEP low_latency / XCCL 的 rank 间锁步**：捕获时 4 个 rank 各跑各的 Python，进度会错开
     一到多层；DeepEP LL 的 dispatch 是**设备侧自旋等 peer** 的 kernel，一旦错位就可能长时间等待，
     把该卡的 launch queue 打满 → 层层反压。A5 去掉 DeepEP 后仍然挂，说明 XCCL/TP 集合通信或
     XPU 捕获本身也在其中起作用。
  2. **XPU 整图捕获的规模上限/驱动问题**：`XMLIR_FORCE_USE_XPU_GRAPH=1` 下，捕获几千个节点时
     驱动侧卡住（每个 rank 命中的 op 都不同，像是“各自卡在自己那条 capture 流上”）。
- **是否已修**：❌ 未修（这是本次任务的主要遗留）。

### F4（已定位，非阻塞但影响判据）捕获桶只有 `bs=1`

- 每 DP rank 只有 1 条在跑（`max_running_requests=4 / dp=4`），所以 decode 图只有 `bs=1` 一个桶。
- 判据里的「bs 桶按 1/2/4/8」需要把 `--max-running-requests` 放到 16（dp4 × 4）才可能出现多桶。

## 5. 对照实验：热路径 op 单独捕获**全部通过**

脚本（都在 `.build/`，不属于仓库代码）：

| 脚本 | 覆盖 | 结果 |
|---|---|---|
| `p17_capture_probe.py` | `x/(x.sum(dim=1)+eps)`（A3/A4 命中的那一行）、`dim=2` 变体、GEMM 等价写法、纯 sum | 全部 `capture done` + `REPLAY_OK`（max abs diff = 0） |
| `p17_op_graph_probe.py` | `kunlun_ops.rmsnorm`、sinkhorn 除法、MLA KV `raw[idx]` gather（`[1,2048,576]`）、`F.linear(1×16384, 36×16384)` | 全部 `capture done` + `REPLAY_OK` |
| `p17_xccl_graph_probe.py` | 4 rank `dist.all_gather_into_tensor` 放进 `torch.cuda.graph` | 4 rank 全部 `capture done` + `REPLAY_OK [1,2,3,4]` |
| `p17_dequant_probe.py` | `per_token_dequant2d_with_mask` 真实形态 | 4 组 `ALL_OK` |

> 结论：**「某个 torch/插件 op 不可捕获」这个假设被证伪**。挂死只在「整网 + 4 rank + 图捕获」这个
> 组合下出现。

## 6. 插件侧改动

### 6.1 已落地的改动

**没有改 `sglang_kunlun/` 或 `01_eb_adp/test/` 下的任何插件源码。** 本轮只新增了实验性辅助脚本

| `.build/p17_bench.py` | 4 并发 × N token 基准（TTFT / 总延迟 / 单请求 tok/s / 聚合 tok/s / 输出文本） |
| `.build/p17_capture_probe.py` / `p17_op_graph_probe.py` / `p17_xccl_graph_probe.py` / `p17_dequant_probe.py` | 把 §5 的对照实验固化成可复跑脚本 |

（注意：`deepep_mode=normal` 下会被框架覆盖，见 F1）。

### 6.2 建议的插件侧改法（下一步，未实施）

1. **捕获期给 DeepEP dispatch 加 rank 锁步**（对应 F3 推断 1）
   - 落点：`sglang_kunlun/...` 或 fork 的 `DeepEPCudaGraphRunnerAdapter`，在 `capture()` 路径上
     于每次 dispatch 前后插入 `torch.distributed.barrier()`（仅在 capture 模式；
     `get_is_capture_mode()` 可取到），把 4 个 rank 重新对齐。
   - 预期：若挂死消失，则定义域确认在 DeepEP/XCCL 的捕获锁步。
2. **捕获期把 DeepEP dispatch/combine 换成「只记录形状、不做通信」的 stub**
   - 落点：`sglang_kunlun/hooks/layers/moe/ep_moe/layer.py` 的 `forward_deepgemm_masked*` /
     `run_moe_core`，capture 模式下走本地 GEMM（`m_grouped_gemm_*_masked_v3` 保留），跳过
     `deepep` 的 FIFO 通信；replay 时由真实 graph 执行。
   - 风险：dispatch 结果（`recv_count`/`masked_m`）在捕获时是假的，graph replay 会复用捕获时的
     **静态 masked_m**——只有所有 rank 每步 token 数完全一致时才正确。**不建议先走这条**。
3. **先做最小验证**：`--dp-size 1`（关 DP attention）跑一次捕获。
   - 若通 → 阻塞点在 DP/DeepEP 的 rank 协同（含 `dp_attn.py` 的 all_gather），
     再按 1) 处理；若还不通 → 落在 XPU 整图捕获规模上，转 4)。
4. **换后端**：`--cuda-graph-backend-decode breakable`（分段捕获，图规模小得多）。
   fork 的 `BreakableCudaGraphBackend` 已在，未在昆仑上验证过。

## 8. 运维注意事项（本轮踩到的）

1. **`kill -9` 卡在 XPU 调用里的进程会把卡打成半坏态**。本轮为图省事 `kill -9` 了一个卡在
   tensor repr（内部 D2H）里的探针，之后该卡 `torch.cuda.init()` 和 alloc 都正常，
   但**任何真实 kernel（`sum`/`div`）永久挂住**——正是 doc/3「最重要的一条」。
   处理：`xpu-smi -fr -i 0,1,2,3`（约 30 s 恢复），然后必须重跑 preflight 的**算力探针**确认。
   正常停服请只 `kill -TERM <launcher>`；launcher 卡在 waitpid 时，只对**纯 CPU 的
   tokenizer/detokenizer worker** 用 `-9`（与 `stop_kunlun.sh` 的分级策略一致）。
2. **端口**：30110 的 dist 端口是 30343（`ZMQ_TCP_PORT_DELTA = 233`），换端口时两边一起看。
3. **同机他人任务**：本轮 4–7 上一直有另一个任务（30120），期间它崩过一次（dev4 Xid），
   该 Xid **不属于** 0–3；判读 dmesg 时必须按 PCI 地址（52:00 / 55:00 / 63:00 / 66:00 才是 0–3）。
