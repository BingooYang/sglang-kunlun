> ## 🔴 最重要的一条：不要 `kill -9` 卡在 XPU 调用里的进程
>
> **这是本次踩得最惨的坑，请先读这一段。**
>
> 对"卡在 XPU 调用里"的进程（特征：CPU 100% 空转、GPU `0% util`、显存不涨）
> 执行 `kill -9`，会在设备上留下**杀不掉的 kernel** —— `xpu-smi` 显示
> `util = 100%`，但 `xpu-smi -q` 的 `Processes` 是 `None`。这种残留会**拖坏整个
> XPU runtime**：之后连 `torch.ones(1024, device='cuda')` + `sync` 都会间歇性挂死。
>
> 更糟的是驱动会**泄漏 "in use" 引用计数**：此后 `xpu-smi -r`（逐卡 HW reset，
> 官方唯一的用户态恢复手段）对**全部 8 张卡**都报
> `XPU ... is currently in use by another process`，**即使没有任何进程持有
> `/dev/xpu0..7` / `/dev/xpuctrl`**（逐 `/proc/*/fd` 扫过）。于是**只能节点级重启**。
>
> **正确做法**
>
> 1. 发现卡死**先等**（XPU 调用自带超时，给它时间自己出来），不要条件反射地杀；
> 2. 确实必须杀时，杀完要确认 **8 张卡都回到 `0 MiB / 0%`** 再起下一个任务
>    （`xpu-smi | grep 98304MiB`）；
> 3. 服务挂了**不要立刻重试**，先看 `xpu-smi` 是否全绿；
> 4. 脚本里那几行 `pkill -9` 清理逻辑**是有代价的**，只在确认没有 XPU 调用在飞时用。

### 两个脚本为适配新环境做的关键改动（EB5 / DSV4 相同）

1. `source tool/env.sh`（不再用已废弃的 `env/kunlun_py_env.sh`）；路径全部换 `workspace/bingoo`。
2. **入口用 `sglang-kunlun-launch`**，不要用 `python -m sglang.launch_server`：
   标准入口在 `load_plugins()` 里先加载 general 插件，此时平台还没解析、
   `_kunlun_pre_shim` 没跑、`sgl_kernel` 没被 stub，fork 的插件一 import
   `sglang.srt.internal.models.*`（→ quantization → `from sgl_kernel import ...`）就炸成
   `<kunlun-alias-stub>` 连锁失败。
3. **`SGLANG_PLUGINS` 白名单里必须带 `kunlun`**（EB5）：该白名单对
   `sglang.srt.platforms` 与 `sglang.srt.plugins` 两个 group 一视同仁，漏了平台插件会被跳过、
   静默回落到 `CudaSRTPlatform`。
4. **`EB5_KUNLUN_ADAPT_DIR` 必须设**（DSV4 也要）：指向
   `01_eb_adp/test/`，否则适配层不加载 —— DSV4 会直接卡在 `_init_raw`。
5. 适配层里写死的旧工作区路径已改成按 `importlib.util.find_spec("sglang_kunlun")` 解析。

## 四、故障时间线与根因（2026-10-17）

| 时间 | 事件 |
|---|---|
| 13:29 / 13:31 / 13:52 | 8 卡 `all_reduce` 探针 **8/8 通过**，XCCL 完整初始化（有 `XCCL version` / `IBGDA init` / `rdma buffer` 日志） |
| 13:40 | EB5 第一次前向报 `kl3ChannelCheckErrors ... status=299` + `CUDA error: wait for noc idle timeout`，8 rank 全崩 |
| 13:40 之后 | 反复用 `kill -9` 清理卡死进程 → **残留 stuck kernel 开始累积** |
| 17:16 | 同一个 XCCL 探针开始挂 |
| 17:30+ | 连 `torch.ones` + `sync` 都间歇性挂；`xpu-smi -r` 对全部卡报 "in use" |

**根因**：设备/驱动的**残留坏状态**（stuck kernel + 泄漏的 "in use" 引用计数），
不是配置或代码问题 —— 同一套 env + 同一个探针，13:52 能过、之后不能。

**判定依据**：`xpu-smi -r` 对全部 8 张卡（含从未运行过任何任务的卡 7）都报
`is currently in use by another process`，但逐 `/proc/*/fd` 扫描**没有任何进程持有
`/dev/xpu0..7` / `/dev/xpuctrl`**，且 `xpu-smi -q` 自己显示 `Processes: None` ——
驱动状态与自身查询结果自相矛盾。

### 最小复现（不需要模型，约 2 分钟）

```bash
source .../01_eb_adp/tool/env.sh
export CUDA_VISIBLE_DEVICES=0,1,2,3,4,5,6,7
# 8 个进程：先 dist.init_process_group(nccl, ws=8)，再做几个 int64 op + .cpu()
for r in 0 1 2 3 4 5 6 7; do ( env RANK=$r WORLD_SIZE=8 python -u /tmp/r8.py & ); done
```

结果（干净机器上稳定复现）：

| 场景 | 结果 |
|---|---|
| 8 进程，**只做** trivial op（无 XCCL） | **8/8 通过** |
| 8 进程 + `init_process_group(nccl, ws=8)` | **5/8**，rank **0/1/2** 挂死 |
| 4 进程（卡 0,1,5,6）+ `ws=4` | **1/4**，rank **0/1/2** 挂死 |

- 挂死点：rank1/2 精确停在 `p8l.cpu()`（**D2H 拷贝**），rank0 更早一点
- 与 `CUDA_VISIBLE_DEVICES` 顺序、进程启动顺序、`XSHMEM_*`/`BKCL_*` 变量**均无关**
- **换卡无效**：失败跟的是 **rank 序号**，不是卡

### 卡本身是好的（别误判为坏卡）

- 8 张卡 ECC（correctable / uncorrectable）**全 0**；
- 只暴露 `{2,3,4}` 跑 3 进程 → **3/3 通过**；只暴露 `{5,6,7}` → **3/3 通过**。


   需要 KLX 侧介入。
